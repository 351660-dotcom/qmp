# 09 · 门票全链路服务契约（OpenAPI + 事件 Schema）

> 落地 ADR-011「API-First + 统一规范」。本文档把 [08 文档第七节](08-门票全链路核心域模型-商品价格支付核销会员.md#七待-task-3-细化的接口事件清单汇总)列出的接口/事件具体化为契约草案，作为后续生成代码/Mock/契约测试的依据。
>
> 范围说明：本文档定义的是**门票全链路 v1 的契约子集**，字段命名/错误码/事件 envelope 的规范本身是全平台统一标准（后续链路直接复用），但具体业务字段会随后续链路（套票、酒店等）扩展。

## 一、全平台统一规范

### 1.1 HTTP 响应格式

```json
{
  "code": "OK",
  "message": "success",
  "data": { },
  "trace_id": "a1b2c3d4"
}
```

- `code = "OK"` 表示业务成功；其余为 `{SERVICE}_{ERROR_NAME}` 格式的业务错误码（大写 snake case）。
- HTTP 状态码与 `code` 联动：
  | HTTP | 含义 | 示例 code |
  |---|---|---|
  | 200 | 业务成功 | `OK` |
  | 400 | 参数校验失败 | `*_INVALID_PARAM` |
  | 404 | 资源不存在 | `*_NOT_FOUND` |
  | 409 | 状态冲突/业务规则拒绝（**调用方应据此判断是否需要走补偿逻辑**） | `*_INSUFFICIENT_STOCK`、`*_INVALID_STATE` |
  | 500 | 系统错误（调用方按重试策略处理） | `INTERNAL_ERROR` |
- `trace_id` 贯穿全链路日志，来自 API 网关注入的 trace header。

### 1.2 幂等规范

- 所有"创建型"写接口的幂等键**显式作为业务字段**（不使用隐式的 `Idempotency-Key` header），具体见各接口定义。本设计复用领域 ID 本身作为幂等键（如 `reservation_id = order_item_id`），符合 ADR-010「显式优于隐式」。
- 幂等语义：相同幂等键的重复请求返回**首次执行的结果**（不报错，不重复执行副作用）。

### 1.3 MQ 事件 Envelope（RocketMQ）

```json
{
  "event_id": "uuid-v4",
  "event_type": "PaymentSucceeded",
  "schema_version": "1.0",
  "tenant_id": 1001,
  "occurred_at": "2026-07-01T10:00:00Z",
  "payload": { }
}
```

- **Topic 命名**：`{domain}.{event-name-kebab}`，如 `payment.payment-succeeded`。
- **去重**：消费方按 `event_id` 写入 `processed_event` 表（`UNIQUE(consumer_group, event_id)`），消费前先查重。
- **顺序性**：同一 `order_id`/`payment_id` 相关事件需保证消费顺序 → MQ 分区 key 取 `order_id`。
- **Schema 注册**：每个 `event_type` 对应一份 JSON Schema，存放于 `docs/contracts/events/{event_type}.schema.json`（本文档先给出结构，后续链路落实际文件）。

## 五、inventory-service

```yaml
openapi: 3.1.0
info: { title: inventory-service, version: "1.0" }
paths:
  /api/v1/inventory/availability:
    get:
      summary: 查询库存余量（C端展示用，非强一致，仅供参考）
      parameters:
        - { name: sku_id, in: query, required: true, schema: { type: integer } }
        - { name: sale_date, in: query, required: true, schema: { type: string, format: date } }
        - { name: time_slot_id, in: query, required: false, schema: { type: integer } }
      responses:
        "200":
          content:
            application/json:
              example: { code: OK, data: { total_quota: 1000, sold_count: 600, locked_count: 50, remain: 350 } }

  /api/v1/inventory/reservations:
    post:
      summary: 创建库存预占（幂等键 = reservation_id，由调用方传入，约定取 order_item_id）
      requestBody:
        content:
          application/json:
            example:
              reservation_id: "OI-20260701-000123"
              sku_id: 1001
              sale_date: "2026-07-01"
              time_slot_id: 1
              quantity: 2
      responses:
        "200":
          content:
            application/json:
              example:
                code: OK
                data: { reservation_id: "OI-20260701-000123", status: HOLDING, hold_expire_at: "2026-07-01T10:15:00Z" }
        "409": { description: "code=INVENTORY_INSUFFICIENT_STOCK" }

  /api/v1/inventory/reservations/{reservation_id}/confirm:
    post:
      summary: 确认预占 HOLDING->CONFIRMED（幂等：重复调用返回当前状态）
      responses:
        "200": { description: "data: { reservation_id, status: CONFIRMED }" }
        "404": { description: "code=INVENTORY_RESERVATION_NOT_FOUND" }
        "409": { description: "code=INVENTORY_RESERVATION_INVALID_STATE（如已是 RELEASED/EXPIRED）" }

  /api/v1/inventory/reservations/{reservation_id}/release:
    post:
      summary: 释放预占 HOLDING|CONFIRMED -> RELEASED（幂等）
      responses:
        "200": { description: "data: { reservation_id, status: RELEASED }" }
        "404": { description: "code=INVENTORY_RESERVATION_NOT_FOUND" }
```

## 六、payment-service

```yaml
openapi: 3.1.0
info: { title: payment-service, version: "1.0" }
paths:
  /api/v1/payments:
    post:
      summary: 创建支付单（幂等键 = order_id，1:1）
      requestBody:
        content:
          application/json:
            example: { order_id: 5001, tenant_id: 1001, merchant_id: 2001, amount: 176.00, channel: WECHAT }
      responses:
        "200":
          content:
            application/json:
              example:
                code: OK
                data:
                  payment_id: "PAY-20260701-005001"
                  status: CREATED
                  pay_params: { prepay_id: "wx20260701...", ... }  # 透传给客户端调起支付SDK，结构由channel决定

  /api/v1/payments/{payment_id}/close:
    post:
      summary: 关闭支付单（订单 pay_expire_at 超时触发，幂等）
      responses:
        "200": { description: "data: { payment_id, status: CLOSED }" }
        "409": { description: "code=PAYMENT_ALREADY_PAID（支付已成功但订单侧才发起关单，调用方应转为正常流程而非报错给用户）" }

  /api/v1/payments/{payment_id}/refunds:
    post:
      summary: 发起退款（幂等键 = credential_id，一张票只能有一条有效退款记录）
      requestBody:
        content:
          application/json:
            example: { credential_id: 9001001, amount: 88.00 }
      responses:
        "200": { description: "data: { refund_id, status: PENDING }" }
```

### 6.1 渠道回调（微信/支付宝 → payment-service，内部端点，不对外暴露 OpenAPI）

- `POST /internal/callbacks/wechat`、`/internal/callbacks/alipay`：验签后更新 `PaymentOrder.status=PAID`，发布 `PaymentSucceeded` 事件。
- 回调签名校验失败：记录日志 + 返回渠道要求的失败响应格式，**不抛异常给业务侧**。

### 8.1 创建订单编排逻辑（伪代码，含补偿）

```
function CreateOrder(user_id, items):
  is_member = member.GetMemberStatus(user_id)
  reserved = []  # 已成功预占的 item，用于失败回滚
  for item in items:
    sku = product.GetSkuInfo(item.sku_id)
    if sku.status != ON_SALE: return 409 PRODUCT_SKU_NOT_ON_SALE

    price = pricing.GetPrice(item.sku_id, item.sale_date, is_member)
    order_item_id = generate_id()  # 提前生成，作为后续幂等键

    try:
      inventory.CreateReservation(order_item_id, item.sku_id, item.sale_date, item.time_slot_id, item.quantity)
      reserved.append(order_item_id)
    except INSUFFICIENT_STOCK:
      for r in reserved:
        inventory.ReleaseReservation(r)          # 补偿：回滚已预占的前序 item
      return 409 INVENTORY_INSUFFICIENT_STOCK(failed_item=item)

  order = persist Order(status=PENDING_PAYMENT, items=[...], pay_expire_at=now+15min)
  return order
```

> **注意**：这是模块化单体阶段的"伪分布式事务"——多个 item 的预占不在同一本地事务内，靠**显式补偿**保证一致性。若拆分为独立微服务后，建议引入 Seata（ADR-001 已选型）做 TCC，但 v1 先用补偿模式跑通链路，避免过早引入分布式事务复杂度。

### 8.2 异步事件消费（order-service 作为消费方）

| 事件 | 来源 | 消费动作（需在本地事务中保证幂等） |
|---|---|---|
| `PaymentSucceeded` | payment-service | 1) `inventory.ConfirmReservation` (per item) 2) `ticket-verification.IssueCredentials` (per item) 3) `Order.status -> PAID` 4) 写 `processed_event` 防重 |
| `TicketVerified` | ticket-verification-service | 更新对应 `OrderItem` 下凭证聚合状态；若该订单所有凭证均为终态，`Order.status -> CLOSED` |
| `RefundSucceeded` | payment-service（经 ticket-verification 转发或直接订阅） | 若退款对应凭证在可释放窗口内，调用 `inventory.ReleaseReservation` |

## 九、契约小结 / 下一步

- 本文档覆盖了 task #3 范围内的全部接口与事件。task #4（DB schema）将基于本文档的字段定义产出 DDL。
- 错误码表（1.1 中的 `*_xxx`）需在实现时收敛为枚举常量类，禁止散落的字符串字面量（ADR-010 显式优于隐式）。
- 后续链路（套票跨商户分账、OTA 渠道库存）会在 inventory/order/payment 的契约上**新增字段**而非修改现有字段语义，保证向后兼容（API 版本管理见 v0.2 第 16 节）。
