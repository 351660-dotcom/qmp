# 06 · 库存与防超卖设计

> 本系统**最核心、最不能出错**的部分。超卖一张（尤其演唱会/节假日爆款）即造成赔付与声誉事故。
> 场景假设：几十万人/秒抢同一爆款票种；多渠道（OTA/直营/B2B）并发；剧院选座不可一座多卖。
> 关联：ADR-014（并发指标）、ADR-018（本设计）。

## 一、核心原则：分层漏斗 + 两道防线

几十万/秒的请求必须逐层收窄到系统可承受量（下单 10,000/秒），不能让全部请求打到库存：

```
几十万/秒
 ① 前端/风控：按钮置灰、验证码/滑块、实名限购、黑名单挡黄牛
 ② 网关限流 + 排队：超承接力进候补队列，秒回"排队中"（不报错）
 ③ Redis 预扣库存：原子、毫秒级、快速失败        ← 第一道防线（挡量）
 ④ MQ 削峰：抢中的异步落库，用户去支付
 ⑤ DB 带条件扣减：UPDATE ... WHERE remain>=N       ← 第二道防线（不超卖最终保证）
```

**两道防线分工**：
- **Redis 挡量 + 快速失败**：抗高并发，秒级反馈。
- **DB 带条件更新是不超卖的最终保证**：`UPDATE stock SET remain = remain - N WHERE id=? AND remain >= N`，影响行数=0 即售罄。即使 Redis 因故障/主从切换多扣，DB 绝不让库存为负。**两者不一致以 DB 为准**，多扣的退款/回补。

## 二、数量库存（门票）——破解单点热点

瓶颈是单个库存 key/row 的争抢（一个点）。解法 **库存分桶**：
- 总库存 N 拆 M 桶分散到不同 Redis 分片（如 1000 张 → 10 桶各 100）。
- 请求按用户哈希到桶扣减 → 单点压力摊到 M 点 → 吞吐 ×M。
- 桶空但他桶有货 → 重试相邻桶；尾部"最后几张"合并兜底。

**异步落库 = MQ 按商品分区 + 单线程顺序消费**：
- 同一票种扣减消息进同一分区，单消费者顺序写 DB → 无行锁争抢、天然不超卖、保证顺序。
- 前置已限流+预扣过滤，该环节量可控。

## 三、多渠道共享库存

- **共享库存**：所有渠道扣同一池，正确性最简单。
- **分配库存（切量）**：渠道预分配额度，防止互相饿死；未售回收。
- **本系统采用：共享池 + 渠道封顶** 混合。
- ⚠️ **OTA 直连**：OTA 缓存我方库存，须及时推送变更；OTA 下单必须回调我方**锁库存接口**真正占位（带幂等键），不信其本地缓存。

## 四、座位库存（剧院选座/游船舱位）

每个座位是唯一资源，状态机：**可售 → 锁定（TTL）→ 已售**。
- 锁座原子操作：`UPDATE seat SET status='locked', owner=?, expire=? WHERE seat_id=? AND status='available'`，影响行数=1 才算抢到。
- 两人同点一座 → 仅一人成功，另一人提示"已被选走" → **根治一座多卖**。
- DB 唯一约束 `(场次, 座位, 已售)` 作最终兜底。
- **TTL 释放**：锁而不付超时自动回"可售"（延时消息/定时扫描）。
- 座位图实时变灰推送其他用户；权威锁定在服务端原子操作，前端展示仅辅助。

## 五、统一的预占模型

**预占（lock）→ 确认（confirm）→ 释放（release）**：
- 数量库存：预占 = available 减、locked 加；支付成功 confirm；超时 release 回 available。
- 座位库存：预占 = 锁座；支付成功 confirm = 已售；超时 release = 解锁。
- 抢票场景预占 TTL 缩短（5 分钟甚至更短）。

## 六、防超卖的隐形杀手（必须全部覆盖）

1. **预占必须有 TTL** —— 占而不付自动释放，否则僵尸订单占死库存。
2. **预扣与落库补偿** —— Redis 扣了但建单失败，须把库存还回（可靠消息/对账补偿）。
3. **幂等** —— 每个下单请求带幂等 token，狂点/重试不重复扣。
4. **实名限购是隐藏热点** —— 一证限购 N 张，按身份证计数同为高并发原子操作；兼合规与防黄牛。
5. **对账兜底** —— 定时核对 Redis 预占量 vs DB 实际订单，修正漂移，以 DB 为准。
6. **Redis 高可用** —— 持久化 + 集群；故障时 DB 带条件更新仍是最后防线。

## 七、对外 API（API-First，见 ADR-011）
- 查库存/查座位图（高频读，多级缓存）
- 锁库存 / 锁座（幂等，供 OTA、C 端、B 端共用）
- 确认 / 释放
- 库存变更事件（Webhook + MQ，推 OTA 与数据中台）
