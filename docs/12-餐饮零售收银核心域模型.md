# 12 · 餐饮零售收银核心域模型

> 范围：功能清单第 10 节「餐饮零售收银」（ADR-008 完整收银 / ADR-017 点单入口范围 / ADR-019 供应链总部-门店协同，含 2026-06-14 绿云 Materials Control 对标细化）。
> 部署形态：延续 07/11 文档的「模块化单体」原则，本域新增两个 Maven 模块：
> - **dining-pos-service**：桌台、排队、点单（含 KDS/沽清）、结账，覆盖堂食与零售即时收银。
> - **supply-chain-service**：总部-门店供应链协同（采购、仓配、中央厨房、领料、成本核算），与 dining-pos-service 通过「BOM 扣减库存」事件交互。
> 范围澄清：本文档的「零售」特指**景区内零售小店的即时收银**（实物 SKU 扫码/称重收银，即买即走）；功能清单第 17 节 C 端「商城/特产购买」是另一条**电商履约链路**（下单→物流配送→收货，独立履约状态机），不在本文档范围内，留待 C 端商城链路专项设计。
> 会员储值抵扣依赖 08 文档 `MemberAccount` 扩展 `MemberWallet`（余额），本文档 4.2 给出最小扩展。

### 1.5 点单项状态机（OrderLine.status）

```
ORDERED(已下单) ──需过厨房(requires_kitchen=true)──▶ SENT_TO_KDS ──厨房确认──▶ COOKING ──出品──▶ READY ──服务员取餐──▶ SERVED(终态)
   │                                                                                                      │
   │ 不需过厨房(如饮料/零售SKU)──▶ SERVED(终态，直接计入账单)                                                │
   │                                                                                                       │
   ├──加菜后未送厨房前取消──▶ CANCELLED(终态，不计入 total_amount)                                          │
   │                                                                                                       │
   └──已下厨/已上菜后申请退菜(需折扣/赠菜权限审批，见 4.3)──────────────────────────────────────────────▶ RETURNED(终态)
```

- **加菜**：对 `OPEN` 状态的 `TableOrder` 新增 `OrderLine`，不影响已有行；`source` 标记来源渠道。
- **退菜**：`ORDERED/SENT_TO_KDS → CANCELLED` 可由店员直接操作（厨房尚未开始制作，无成本损耗）；`COOKING/READY/SERVED → RETURNED` 需走「折扣/赠菜权限审批」（4.3），因为已产生原料损耗（与五、6.3 成本核算联动——`RETURNED` 的原料消耗仍计入损耗，不退回库存）。
- **并台**：两个 `TableOrder(OPEN)` 合并为一个——保留其中一个为主单，将另一单的全部 `OrderLine` 迁移过来（`table_order_id` 重写），另一单转 `VOIDED`，关联的 `DiningTable` 释放为 `IDLE`（如整桌迁走）或保留（如临时拼桌）。
- **转台**：`TableOrder.table_id` 变更，原桌 `OCCUPIED→IDLE`（生成清洁提示，可选）/`CLEANING`，新桌 `IDLE→OCCUPIED`。

### 2.1 实体：KitchenTicket（厨房工单）

| 字段 | 类型 | 说明 |
|---|---|---|
| `kitchen_ticket_id` | bigint (PK) | |
| `merchant_id` | bigint | |
| `station` | varchar | 出品档口（热菜/凉菜/饮品等，按 `sku_id` 所属分类路由） |
| `order_line_ids` | json (bigint[]) | 同一桌同一档口的多个 `OrderLine` 可合并为一张工单 |

### 2.2 菜品沽清：DishAvailability

| 字段 | 类型 | 说明 |
|---|---|---|
| `sku_id` | bigint (PK) | |
| `merchant_id` | bigint | |
| `status` | enum | `AVAILABLE` / `SOLD_OUT` |
| `updated_at` | datetime | |

- 厨房/前厅任意一端标记 `SOLD_OUT` → 实时同步（事件广播）至：顾客扫码点单页（商品中心 `GetSkuInfo` 返回中附带该状态）、PDA 代客下单、（若有）线上点餐入口，三端必须**一致**（哗啦啦/客如云对标的核心体验点）。

- 与五、供应链的关系：`DishAvailability` 是**前厅运营状态**（可人工标记，不等于库库存为 0），但 `SkuStock`（5.2）库存触发的预警可作为自动标记 `SOLD_OUT` 的参考信号（v1 为提示，不自动强制下架，避免误判主辅料共享导致误停售）。

## 三、零售订单（即时收银，无桌台）

- 复用 `TableOrder`（`table_id=null`），开台即结账：`status` 直接 `OPEN→SETTLING→CLOSED`（无 `OCCUPIED` 占用周期）。
- `OrderLine.sku_id` 为零售 SKU（`requires_kitchen=false`），`status` 直接 `ORDERED→SERVED`，无 KDS 流程。
- 条码秤称重商品：`OrderLine.quantity` 为称重数量（如 0.5kg），`unit_price_snapshot` 为单价（元/kg），`subtotal = unit_price × quantity`。

## 四、结账（Checkout）

### 4.1 结账流程

1. `TableOrder: OPEN→SETTLING`（发起结账，校验所有 `OrderLine.status ∈ {SERVED, CANCELLED, RETURNED}`，不存在仍在 `COOKING`/`READY` 的行——避免结账后又上菜）。
2. 计算应付金额：`payable = Σ(SERVED 行 subtotal) - 折扣（4.3） - 会员储值抵扣（4.2）`。
3. 聚合支付：`payable > 0` 部分走 payment-service（07/08 文档的 `PaymentOrder`，渠道微信/支付宝/现场 POS，纳入第 7 节统一对账）；酒店 Room Service 场景（11 文档 7.2）`payable` 全额走「挂房账」，本服务侧记 0 元实收。
4. `TableOrder: SETTLING→CLOSED`；`DiningTable: OCCUPIED→CLEANING`（若有桌台）。
5. 触发五、6.3 按 BOM 核减门店库存（异步事件，不阻塞结账主流程——核减失败仅记录异常，不回滚已完成的支付）。

### 4.2 会员储值抵扣（member-service 最小扩展）

| 字段 | 类型 | 说明 |
|---|---|---|
| `user_id` | bigint (PK) | 同 08 文档 `MemberAccount.user_id` |
| `wallet_balance` | decimal | 储值余额（集团级，ADR-009） |

- `DeductWallet(user_id, amount) -> {success, remaining_balance}`：结账时调用，扣减成功记一条 `FolioItem` 式的「钱包消费记录」（归属 member-service，对账纳入第 7 节）；余额不足则该部分转入聚合支付，不允许「部分扣减+部分失败」的歧义状态（即：要求 `amount ≤ wallet_balance`，否则整笔储值抵扣金额为 0，全额走聚合支付，由前端在结账前提示用户）。
- 储值充值（11 文档「园内二次消费钱包」提到的腕带/手牌余额场景）属于充值链路，不在本文档范围，仅消费侧复用同一 `wallet_balance`。

### 4.3 折扣/赠菜权限与反结账审批

| 字段 | 类型 | 说明 |
|---|---|---|
| `approval_id` | bigint (PK) | |
| `table_order_id` | bigint | |
| `type` | enum | `DISCOUNT`(整单折扣) / `FREE_ITEM`(赠菜/单品免单) / `RETURN_AFTER_COOK`(已制作退菜) / `REOPEN`(反结账) |
| `applicant_id` / `approver_id` | bigint | 发起人/审批人（权限按角色：店员→店长→区域经理，三级管控对标客如云） |
| `status` | enum | `PENDING` → `APPROVED` / `REJECTED` |
| `reason` | varchar | |

- `REOPEN`（反结账）：`TableOrder: CLOSED→OPEN`，要求 `approval.type=REOPEN` 且 `APPROVED`；反结账后原支付记录需先发起退款（payment-service）才能修改 `OrderLine`，避免「账目已收款但订单内容被改」的不一致——与功能清单第 6 节「异常订单处理工作台」共用工单机制。
- `DISCOUNT`/`FREE_ITEM`/`RETURN_AFTER_COOK` 在 `PENDING` 期间，对应 `OrderLine`/`TableOrder.total_amount` 暂不变更，`APPROVED` 后才生效，保证审批留痕与金额变更同源。

## 五、供应链数字化（supply-chain-service，总部-门店协同，ADR-019）

> 这是本域工程量最大、最具「总部-门店协同」特征的部分（对标哗啦啦/客如云总部-门店供应链协同 + 绿云 Materials Control 多级审批/无纸化领料/POS 自动核减）。

### 5.3 多级采购审批：PurchaseOrder

| 字段 | 类型 | 说明 |
|---|---|---|
| `purchase_order_id` | bigint (PK) | |
| `tenant_id` | bigint | 总部统一采购计划 |
| `target_warehouse_id` | bigint | 收货仓库（通常为 `HQ` 总部仓或 `CENTRAL_KITCHEN`） |
| `supplier_id` | bigint | 供应商档案（轻量主数据，本文档不展开） |
| `items` | json | `[{sku_id, quantity, unit_price}]` |
| `status` | enum | 见状态机 |

```
DRAFT ──提交──▶ PENDING_APPROVAL(L1) ──通过──▶ PENDING_APPROVAL(L2) ──通过──▶ APPROVED ──下单──▶ ORDERED ──收货──▶ RECEIVED(终态)
   │                    │                              │

   └──取消──▶ CANCELLED(终态)
```

### 5.4 门店订货与供应链接单：StoreOrderRequest + TransferOrder

**StoreOrderRequest（门店订货单）**

| 字段 | 类型 | 说明 |
|---|---|---|
| `request_id` | bigint (PK) | |
| `store_warehouse_id` | bigint | 门店仓（`owner_scope=STORE`） |
| `items` | json | `[{sku_id, quantity}]` |
| `status` | enum | `SUBMITTED` → `ACCEPTED`(供应链中心接单) → `FULFILLED`（关联 `TransferOrder` 完成） / `REJECTED`(库存不足等) |

**TransferOrder（调拨单）**

| 字段 | 类型 | 说明 |
|---|---|---|
| `transfer_order_id` | bigint (PK) | |
| `source_warehouse_id` / `target_warehouse_id` | bigint | 如 `HQ仓/中央厨房 → 门店仓` |
| `items` | json | `[{sku_id, quantity}]` |
| `status` | enum | `CREATED` → `SHIPPED` → `RECEIVED`（终态） |
| `source_ref` | varchar | 关联 `StoreOrderRequest.request_id`（门店订货触发）或人工/补货策略触发（为空） |

- `StoreOrderRequest: ACCEPTED` → 供应链中心生成 `TransferOrder`（校验 `source_warehouse_id` 的 `SkuStock.quantity >= 申请量`，不足则部分发货 + 标记 `StoreOrderRequest` 差异，对标"实时数据流"门店与供应链共享库存可见性）。

### 5.5 中央厨房加工：ProcessingOrder

| 字段 | 类型 | 说明 |
|---|---|---|
| `processing_order_id` | bigint (PK) | |
| `central_kitchen_warehouse_id` | bigint | |

### 5.6 无纸化领料：RequisitionForm（门店仓 → 出品消耗）

| 字段 | 类型 | 说明 |
|---|---|---|
| `requisition_id` | bigint (PK) | |
| `store_warehouse_id` | bigint | |
| `items` | json | `[{sku_id, quantity}]` |
| `requested_by` | bigint | 后厨领料人 |
| `status` | enum | `SUBMITTED` → `APPROVED`(店长/库管确认) → `ISSUED`(终态，已出库) |

- `ISSUED` → `SkuStock.quantity -= items`（门店仓 → 出品台，出品台不单独建模为 `Warehouse`，视为消耗终点）。
- 与 6.3「POS 销售自动核减库存」的关系：领料是**计划性/批量**出库（如早班领取当日预估用量到出品台），POS 核减是**实时/按单**核减门店仓库存——v1 两者**不重复扣减同一份库存**：`RequisitionForm` 扣减门店仓 `SkuStock`，`OrderLine` 结账后的 BOM 核减默认作用于**领料后的"在制可用量"**（v1 简化为同一 `SkuStock` 记录，允许临时为负并在盘点时调整，负值代表"已领料但未及时补单"的正常业务延迟，不触发告警阈值之外的强阻断）。

| `book_quantity` | decimal | 账面结存（盘点时点的 `SkuStock.quantity`） |
| `actual_quantity` | decimal | 实盘数量 |
| `variance` | decimal | = `actual - book`，负值为**损耗** |
| `counted_at` / `counted_by` | - | |

- 盘点完成后，`SkuStock.quantity` 以 `actual_quantity` 校正（生成一条调整记录，差异计入损耗成本，供第 14 节「餐饮成本/损耗分析报表」消费）。

## 六、菜品 BOM 与成本核算

### 6.1 实体：DishBom（用料表）

| 字段 | 类型 | 说明 |
|---|---|---|
| `bom_id` | bigint (PK) | |
| `output_sku_id` | bigint | 产出 SKU（菜品/半成品/成品） |
| `output_quantity` | decimal | 产出数量（如「1 份」「10kg」） |
| `materials` | json | `[{material_sku_id, quantity, unit}]` 原料用量，单位需与 5.2 `SkuStock.unit` 一致或定义换算系数 |

### 6.2 成本核算：CostSnapshot

| 字段 | 类型 | 说明 |
|---|---|---|
| `order_line_id` | bigint (PK) | 关联 1.4 `OrderLine`（仅 `requires_kitchen=true` 的菜品行） |
| `bom_id` | bigint | 结账时使用的 BOM 版本（快照，避免 BOM 后续调整影响历史成本） |
| `material_cost` | decimal | 按 BOM 用量 × 当前原料成本价计算（成本价取 5.3 `PurchaseOrder` 最近一次 `unit_price` 或加权平均，v1 取最近一次） |
| `revenue` | decimal | = `OrderLine.subtotal` |
| `gross_margin` | decimal | = `revenue - material_cost` |

### 6.3 POS 销售数据自动核减库存（绿云 Materials Control 对标）

```
TableOrder: SETTLING → CLOSED（结账完成事件）
        │
        ▼
for each OrderLine where status = SERVED and sku.requires_kitchen = true:
    bom := DishBom(sku_id = OrderLine.sku_id)
    for each material in bom.materials:
        SkuStock(store_warehouse, material.material_sku_id).quantity -= material.quantity × OrderLine.quantity
        （条件更新，允许临时为负，见 5.6 说明；核减失败仅记录异常，不回滚结账）
    生成 CostSnapshot(order_line_id, bom_id, material_cost, revenue, gross_margin)

for each OrderLine where status = RETURNED:
    仅生成 CostSnapshot（损耗计入），不再额外核减库存（库存已在首次 SERVED→结账时核减或在 COOKING 阶段已消耗原料，RETURNED 不退料）
```

- 该事件为**异步**（不阻塞结账主流程），消费方为 supply-chain-service；若核减失败（如 `DishBom` 未配置），记录到「异常订单处理工作台」由库管补录后重放。
- 库存预警（5.2 `reorder_point`）在每次核减后检查，触发后推送给店长（移动管理端，11 文档 4.6 同类机制）与数据中台。
