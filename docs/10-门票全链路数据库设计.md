> 承接 [07](07-门票全链路核心域模型.md)/[08](08-门票全链路核心域模型-商品价格支付核销会员.md)/[09](09-门票全链路服务契约.md)，给出核心表 DDL。
> 范围：门票全链路 13 张表，覆盖 inventory/order/product/pricing/payment/ticket-verification/member 七个服务。

## 一、通用约定

1. **主键生成**：所有业务主键（除 `reservation_id`/`payment_id`/`refund_channel_no` 等天然字符串 ID）使用**应用层雪花算法（Snowflake）**生成的 `BIGINT UNSIGNED`，不使用数据库自增列——自增列在未来分库分表下会产生冲突，雪花 ID 自带时间序，跨分片唯一且趋势递增。
2. **多租户隔离**：每张业务表都有 `tenant_id` 列并建立索引；所有 DAO 查询**强制带 `tenant_id` 条件**（ORM 层拦截器统一注入，禁止裸写 SQL 漏加），落地 ADR-021「三不干涉」的数据隔离要求。
3. **时间字段**：统一 `created_at` / `updated_at`（除纯日志型表只有 `created_at`），均为 `DATETIME`，应用层写入 UTC。
4. **金额字段**：统一 `DECIMAL(10,2)`。
5. **枚举字段**：用 `VARCHAR` 而非 MySQL `ENUM`，避免后续扩枚举值需要 `ALTER TABLE`；取值范围在应用层用常量枚举类约束（ADR-010 显式优于隐式）。
6. **`order` 为 MySQL 保留字**，表名改为 `trade_order`。

## 五、库存域（ADR-018 防超卖核心）

### 5.1 inventory_bucket

```sql
CREATE TABLE inventory_bucket (
  bucket_id     BIGINT UNSIGNED NOT NULL,
  tenant_id     BIGINT UNSIGNED NOT NULL,
  scenic_id     BIGINT UNSIGNED NOT NULL,
  sku_id        BIGINT UNSIGNED NOT NULL,
  sale_date     DATE            NOT NULL,
  time_slot_id  BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '无分时预约固定为0',
  total_quota   INT             NOT NULL,
  sold_count    INT             NOT NULL DEFAULT 0,
  locked_count  INT             NOT NULL DEFAULT 0,
  channel_quota JSON            NOT NULL COMMENT 'v1: {"direct": total_quota}',
  version       INT             NOT NULL DEFAULT 0 COMMENT '乐观锁',
  created_at    DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at    DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (bucket_id),
  UNIQUE KEY uk_sku_date_slot (sku_id, sale_date, time_slot_id),
  KEY idx_tenant_scenic_date (tenant_id, scenic_id, sale_date),
  CONSTRAINT chk_inventory_not_oversell CHECK (sold_count + locked_count <= total_quota)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

> `CHECK` 约束在 MySQL 8.0.16+ 才真正生效，作为**最后一道保险**；主要防线仍是下面三条**条件 UPDATE**（影响行数=0 即视为失败/拒绝）：

```sql
-- CreateReservation：HOLDING（DB 第二道防线，Redis 第一道防线见 07 文档 1.3）
UPDATE inventory_bucket
SET locked_count = locked_count + :qty, version = version + 1
WHERE bucket_id = :bucket_id
  AND total_quota - sold_count - locked_count >= :qty;

-- ConfirmReservation：HOLDING -> CONFIRMED
UPDATE inventory_bucket
SET locked_count = locked_count - :qty, sold_count = sold_count + :qty, version = version + 1
WHERE bucket_id = :bucket_id AND locked_count >= :qty;

-- ReleaseReservation（从 HOLDING 释放）
UPDATE inventory_bucket
SET locked_count = locked_count - :qty, version = version + 1
WHERE bucket_id = :bucket_id AND locked_count >= :qty;

-- ReleaseReservation（从 CONFIRMED 释放，对应已支付后退票）
UPDATE inventory_bucket
SET sold_count = sold_count - :qty, version = version + 1
WHERE bucket_id = :bucket_id AND sold_count >= :qty;
```

## 十、分库分表规划（v1 不启用，预留路径）

v1（模块化单体）阶段：单 MySQL 实例，按服务划分独立 database（与 07 文档"独立 schema"一致），**所有表不分库分表**。所有主键已用雪花 ID（而非自增），`tenant_id` 已作为索引列，为下表的未来分片策略铺路：

| 表 | 分库 key | 分表 key | 说明 |
|---|---|---|---|
| `inventory_bucket` / `inventory_reservation` | `tenant_id` | `sale_date`（按月） | 按景区旺季月份数据量评估是否分表 |
| `trade_order` / `order_item` | `tenant_id` | `hash(user_id)` | 定时扫描任务（超时关单/预占过期）需在每个分片各自调度，不能跨分片 `ORDER BY` |
| `ticket_credential` | `tenant_id` | 随 `order_item` 同分片 | 通过 `order_item_id` 路由 |
| `verification_record` | `tenant_id` | `verified_at`（按月） | 仅追加写，历史数据归档到 ClickHouse/Doris |
| `payment_order` / `settlement_record` / `refund_record` | `tenant_id` | `payment_id`（雪花ID自带时间序，range） | |
| `price_calendar` | `tenant_id` | `sale_date`（按年） | |
| `ticket_product` / `ticket_sku` / `member_account` | `tenant_id` | 不分表 | 数据量级小，单表可支撑到千万级租户 |

启用时机：当任一表行数接近 ShardingSphere 分片阈值（经验值约 5000 万行/表）或单租户私有化部署需要物理隔离时，按 `tenant_id` 分库优先落地（与 ADR-021 数据自主权/导出能力天然契合）。

## 十一、本文档涉及的设计决策记录（按用户指示自主决定，供事后 review）

1. **主键策略**：全部采用应用层雪花 ID，放弃数据库自增列。*理由*：自增列在分库分表后会冲突，且雪花 ID 自带时间序，对 `payment_id` 等需要 range 分片的表更友好。
2. **表名 `order` → `trade_order`**：避开 MySQL 保留字。
3. **`verify_code` 加唯一索引**：核验时需要 `O(1)` 按 `verify_code` 查找凭证，且理论上不会冲突（含签名）。
4. **`verification_record` 冗余 `scenic_id`**：避免在园人数统计时 join `ticket_credential`/`order_item`，牺牲少量存储换查询性能（该表数据量最大）。
5. **`payment_order` / `settlement_record` 均为 1:1**：v1 仅两级分账、单商户购物车，故都加了 `UNIQUE KEY`；后续链路若支持购物车跨商户结算，需要拆分为 1:N 并去掉该唯一约束（已在表注释中标注，避免后续误判为 bug）。
6. **枚举值用 VARCHAR 而非 ENUM**：所有状态字段，便于后续扩展取值不需 DDL 变更。
7. **`processed_event` 表按消费者分别建**：而非全局共享一张表，避免不同消费者的去重逻辑相互阻塞/表行数耦合增长。
