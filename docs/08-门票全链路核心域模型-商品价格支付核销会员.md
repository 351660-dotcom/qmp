# 08 · 门票全链路核心域模型（商品 / 价格 / 支付分账 / 核销 / 会员）

> 承接 [07-门票全链路核心域模型.md](07-门票全链路核心域模型.md)，补齐其余 5 个服务的轻量域模型。
> 这些服务在 v1 范围内职责单一、状态机简单，详细程度低于库存/订单服务；后续链路（套票、酒店、餐饮等）会反过来扩展它们。

---

## 一、商品服务（product-service）

### 1.1 聚合根：TicketProduct（门票 SPU）

| 字段 | 类型 | 说明 |
|---|---|---|
| `product_id` | bigint (PK) | |
| `tenant_id` / `scenic_id` / `merchant_id` | bigint | 归属 |
| `name` / `description` | varchar/text | |
| `status` | enum | `DRAFT` / `PENDING_REVIEW` / `ON_SALE` / `OFF_SALE` |
| `valid_period_rule` | json | 有效期规则（指定日期 / 购买后 N 天内有效等），v1 仅支持「指定可售日期范围」 |
| `real_name_rule` | enum | `NONE` / `ONE_TICKET_ONE_ID`（一票一证）/ `ONE_ORDER_MULTI_PERSON`（一单多人） |

### 1.2 实体：TicketSku（票种）

| 字段 | 类型 | 说明 |
|---|---|---|
| `sku_id` | bigint (PK) | 库存桶、订单项、价格日历均以此为关联键 |
| `product_id` | bigint | |
| `ticket_type` | enum | `ADULT` / `CHILD` / `SENIOR` / `STUDENT` / `MILITARY` |
| `requires_time_slot` | bool | 是否分时预约 |
| `time_slot_definitions` | json, nullable | 若 `requires_time_slot=true`，定义可选时段列表（如 `["09:00-11:00","11:00-13:00"]`） |

### 1.3 上下架审核流（实体：ProductReviewRecord）

```
DRAFT ──提交审核──▶ PENDING_REVIEW ──通过──▶ ON_SALE ──下架──▶ OFF_SALE
                          │
                          └──驳回──▶ DRAFT
```

`ON_SALE → OFF_SALE` 不影响已售出的历史订单（OrderItem 已快照 sku 信息）。

### 1.4 对外接口（供 order-service 调用）

- `GetSkuInfo(sku_id) -> {product_id, status, ticket_type, real_name_rule, requires_time_slot}`：创建订单时校验 `status == ON_SALE`，否则拒绝下单。

## 二、价格服务（pricing-service）

### 2.1 聚合根：PriceCalendar（价格日历）

| 字段 | 类型 | 说明 |
|---|---|---|
| `price_calendar_id` | bigint (PK) | |
| `sku_id` | bigint | |
| `sale_date` | date | |
| `price_type` | enum | v1 仅 `RETAIL`（门市价）/ `MEMBER`（会员价） |
| `price` | decimal | |

唯一约束：`(sku_id, sale_date, price_type)` 唯一。若某天某 SKU 缺少 `MEMBER` 价格记录，取 `RETAIL` 价格兜底。

### 2.2 对外接口

- `GetPrice(sku_id, sale_date, is_member) -> price`：
  - `is_member=true` 且存在 `MEMBER` 价格 → 返回会员价；否则返回门市价。
  - 该结果在订单创建时被 order-service **快照**到 `OrderItem.unit_price`，价格日历后续变更不影响已下单订单。

### 2.3 v1 范围说明

- 渠道价、协议价、动态调价规则（早鸟/淡旺季）、改价审批流：留待后续链路（OTA 对接、旅行社协议）补充，v1 仅验证「价格快照」机制本身。

## 三、支付分账服务（payment-service）

### 3.1 聚合根：PaymentOrder（支付单）

| 字段 | 类型 | 说明 |
|---|---|---|
| `payment_id` | varchar (PK) | |
| `order_id` | bigint | 与 order-service 的 `Order` 一一对应（v1 单商户购物车） |
| `tenant_id` / `merchant_id` | bigint | |
| `amount` | decimal | = `Order.total_amount` |
| `channel` | enum | `WECHAT` / `ALIPAY`（ADR-015） |
| `status` | enum | `CREATED` → `PAID` / `CLOSED`（支付超时由 order-service 的 `pay_expire_at` 驱动调用 `ClosePayment`） |
| `channel_trade_no` | varchar | 第三方支付交易号 |
| `paid_at` | datetime | |

### 3.2 实体：SettlementRecord（分账记录）

| 字段 | 类型 | 说明 |
|---|---|---|
| `settlement_id` | bigint (PK) | |
| `payment_id` | varchar | |
| `merchant_id` | bigint | |
| `platform_amount` | decimal | 平台抽佣（v1：固定比例） |
| `merchant_amount` | decimal | 商户应得 = `amount - platform_amount` |
| `status` | enum | `PENDING` → `SETTLED` / `FAILED` |
| `settle_channel_no` | varchar | 存管通道分账流水号（ADR-004） |

v1 为**两级分账**（平台 + 单商户），多级抽佣（集团/景区也参与分账）留待后续链路。

### 3.3 实体：RefundRecord（退款记录）

| 字段 | 类型 | 说明 |
|---|---|---|
| `refund_id` | bigint (PK) | |
| `payment_id` | varchar | |
| `credential_id` | bigint | 关联具体哪张票（支持部分退） |
| `amount` | decimal | 按 `OrderItem.refund_policy_snapshot` 计算 |
| `status` | enum | `PENDING` → `SUCCEEDED` / `FAILED` |
| `refund_channel_no` | varchar | |

### 3.4 状态机与事件

```
CREATED ──支付成功(渠道回调)──▶ PAID ──触发分账──▶ (SettlementRecord: PENDING→SETTLED)
   │
   └──pay_expire_at 超时──▶ CLOSED

PAID ──申请退票(来自 TicketCredential.REFUNDING)──▶ (RefundRecord: PENDING→SUCCEEDED/FAILED)
```

- 事件 `PaymentSucceeded(order_id, payment_id, paid_at)`：order-service 消费后驱动 `Order: PENDING_PAYMENT→PAID`（见 07 文档 2.4）。
- 事件 `RefundSucceeded(credential_id, refund_id)` / `RefundFailed(credential_id)`：ticket-verification-service 消费后驱动 `TicketCredential: REFUNDING→REFUNDED` 或回退为 `UNUSED`（见 07 文档 2.5）。

## 四、核销服务（ticket-verification-service）

> `TicketCredential` 聚合根已在 07 文档 2.3 定义，此处补充核验记录与凭证签名机制。

### 4.1 实体：VerificationRecord（核验记录，含失败记录）

| 字段 | 类型 | 说明 |
|---|---|---|
| `verification_id` | bigint (PK) | |
| `credential_id` | bigint | |
| `terminal_id` | varchar | 核验终端（v1 为线上 API，terminal_id 可为小程序/H5 标识；闸机/PDA 留待硬件接入链路） |
| `result` | enum | `SUCCESS` / `ALREADY_VERIFIED`（防重核） / `EXPIRED` / `INVALID_SIGNATURE` |
| `verified_at` | datetime | |

### 4.2 凭证签名（为离线核销预留）

- `verify_code = Base64(credential_id ‖ sku_id ‖ sale_date ‖ HMAC-SHA256(secret, credential_id‖sku_id‖sale_date))`
- v1 在线核验：服务端校验签名 + 查 `TicketCredential.status == UNUSED` + 写 `VerificationRecord(SUCCESS)` + `TicketCredential → VERIFIED`。
- 离线场景（后续链路）：边缘节点持有 `secret` 的验证密钥，可离线校验签名 + 本地黑名单防重复，事后批量同步 `VerificationRecord`。

### 4.3 在园人数统计（v1 简化）

- v1：当日 `VerificationRecord(SUCCESS)` 累计数，按 `scenic_id` + `date` 聚合，作为「在园人数」近似值（不做精确出园追踪）。
- 精确出园核验、⚠️ 承载量预警阈值告警留待后续链路（涉及硬件接入与数据中台实时大屏）。

### 4.4 对外接口

- `IssueCredentials(order_item_id, sku_id, sale_date, quantity, refund_policy_snapshot) -> [credential_id...]`：order-service 在 `Order → PAID` 时调用，幂等键为 `order_item_id`（重复调用返回已生成的凭证列表）。
- `VerifyTicket(verify_code, terminal_id) -> {result, credential_id}`
- `RequestRefund(credential_id) -> refund_id`：校验 `TicketCredential.status == UNUSED` 且符合 `refund_policy_snapshot` 的可退窗口，置为 `REFUNDING` 并调用 payment-service `CreateRefund`。

## 五、会员服务（member-service，最小化）

### 5.1 聚合根：MemberAccount

| 字段 | 类型 | 说明 |
|---|---|---|
| `user_id` | bigint (PK) | 与 C 端用户账号一致 |
| `tenant_id` | bigint | 集团级通会员（ADR-009），`user_id` 在租户内唯一 |
| `is_member` | bool | v1 仅此布尔位 |
| `member_since` | datetime | |

### 5.2 对外接口

- `GetMemberStatus(user_id) -> is_member`：order-service 创建订单时调用，结果传给 pricing-service 的 `GetPrice`。
- 积分、储值、等级、跨商户分摊结算规则（v0.2 第 11 节）：留待会员/营销链路专项设计。

## 六、服务依赖关系总览（更新版）

```
                    ┌──────────────┐
                    │ member-service│◀───────────────┐
                    └──────────────┘                  │
┌───────────────┐   ┌──────────────┐   ┌─────────────┴────┐
│ product-service│◀──┤              │   │                   │
└───────────────┘   │ order-service ├──▶│ pricing-service   │
┌───────────────┐   │  (Order/      │   └───────────────────┘
│inventory-service│◀─┤   OrderItem)  │
└───────────────┘   │               ├──▶┌───────────────────┐
                     │               │   │ payment-service    │
                     │               │◀──┤ (含分账/退款)       │
                     │               │   └───────────────────┘
                     │               ├──▶┌───────────────────┐
                     │               │◀──┤ ticket-verification│
                     └──────────────┘   │ (含TicketCredential)│
                                          └───────────────────┘
```

所有跨服务调用均挂在 `order-service` 上（订单服务是门票全链路的编排中心），其余服务之间无直接依赖——符合模块化单体阶段「边界清晰、易于后续拆分」的要求。
