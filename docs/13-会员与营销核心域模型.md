# 13 · 会员与营销核心域模型

> 范围：功能清单第 11 节「会员与营销」（ADR-009 集团级通会员，含 2026-06-14 新增「营销规则引擎」「声誉/评价管理」）。
> 部署形态：延续 07/11/12 文档的「模块化单体」原则，本域新增两个 Maven 模块：
> - **member-service**：账户域——会员账户/等级成长值/积分账本/储值账本。交易链路强依赖（下单时查会员价、结账时扣储值/积分），要求高可用低延迟。已在 08 文档以最小化形式存在（`MemberAccount.is_member`），本文档为完整扩展。
> - **marketing-service**：营销侧——营销规则引擎、优惠券、秒杀/拼团/砍价活动、分销、人群圈选与触达、声誉管理。非交易关键路径，可独立演进。
> 与已有文档的关系：11 文档 `GuestProfile`、12 文档 `MemberWallet` 均在此处给出权威定义（此前为最小化占位）；秒杀活动的库存桶按 ADR-025 独立建表，复用 `inventory-kernel`。

## 二、跨商户费用分摊结算规则（核心难点）

> ADR-009 指出「需设计积分/券跨商户核销的费用分摊结算规则」；2026-06-14 新增的营销规则引擎进一步扩大了需要分摊的场景（跨商户买赠、返现的平台/商户分担）。本节统一设计**分摊计算与分账调整**机制，不改变 08 文档 3.2 `SettlementRecord` 的「两级分账」基本模型，而是作为其上的**调整项（adjustment）**叠加。

### 2.1 典型场景

| 场景 | 问题 |
|---|---|
| 积分核销 | 用户在商户 A 消费产生积分（`PointLedger.source_merchant_id=A`），在商户 B 用积分抵扣消费（`type=REDEEM, source_merchant_id=B`）。B 少收了钱，但积分是 A "发行"的成本，应由 A 承担还是平台承担？ |
| 跨商户买赠 | 买 A 商品送 B 商品（功能清单 11 节），赠品成本由 B 承担多少比例？ |
| 返现 | 消费后返现到 `MemberWallet`，是平台补贴还是商户自付？ |

### 2.2 聚合根：CostAllocationRule（成本分摊规则，marketing-service）

| 字段 | 类型 | 说明 |
|---|---|---|
| `rule_id` | bigint (PK) | |
| `tenant_id` | bigint | |
| `scenario` | enum | `POINT_REDEMPTION` / `PROMOTION_GIFT` / `CASHBACK` |
| `allocation_method` | enum | `PLATFORM_FULL`(平台全担) / `ISSUER_PAYS`(积分发行商户/赠品赠送商户承担) / `REDEEMER_PAYS`(核销/被赠商户承担) / `SPLIT_RATIO`(按比例分摊) |
| `split_ratio` | json, nullable | `allocation_method=SPLIT_RATIO` 时：`{"platform": 0.3, "issuer_merchant": 0.7}` 等 |

### 2.3 实体：CostAllocationRecord（分摊记录）

| 字段 | 类型 | 说明 |
|---|---|---|
| `record_id` | bigint (PK) | |
| `scenario` | enum | 同 2.2 |
| `order_id` | bigint | 触发分摊的订单（核销/被赠订单） |
| `amount` | decimal | 分摊总金额（积分核销抵扣的金额 / 赠品成本价 / 返现金额） |
| `allocations` | json | `[{party_type: PLATFORM\|MERCHANT, party_id, amount}]`，`Σamount` = 上面 `amount` |
| `settlement_id` | bigint, nullable | 关联 08 文档 `SettlementRecord`，写入后由 payment-service 在分账时作为扣减/补偿项 |

### 2.4 计算与分账调整时序

```
Order: PENDING_PAYMENT → PAID（事件）
        │
        ▼
marketing-service 消费事件，检查该订单是否涉及：
  - PointLedger(REDEEM)（积分抵扣）
  - PromotionRule(GIFT/CASHBACK) 命中记录（三、3.4 应用时快照在订单上）
        │
        ▼
按 CostAllocationRule 计算 CostAllocationRecord.allocations
        │
        ▼
payment-service 生成 08 文档 SettlementRecord 时，读取本订单关联的 CostAllocationRecord：
  - merchant_amount（核销/被赠商户应得）按 allocations 中该商户承担的金额扣减
  - 平台承担部分计入 platform_amount 的反向调整（即平台为此让出部分抽佣或倒补）
  - 其他承担商户（如积分发行商户）生成额外一条 SettlementRecord 调整分账（跨商户资金流转仍在存管通道内，符合 ADR-004）
```

- **一致性**：`CostAllocationRecord` 与对应的 `SettlementRecord` 调整在同一事务/同一 MQ 事务消息内提交，避免"分摊算了但分账没扣"或反之。
- **可追溯**：所有营销优惠在订单/分账明细中可追溯到承担方（功能清单要求），即查询任一 `order_id` 可还原 `CostAllocationRecord.allocations` 与对应 `SettlementRecord` 调整记录。

## 三、营销规则引擎（marketing-service）

### 3.1 聚合根：PromotionRule

| 字段 | 类型 | 说明 |
|---|---|---|
| `rule_id` | bigint (PK) | |
| `tenant_id` | bigint | |
| `scope` | enum | `MERCHANT` / `SCENIC`(景区内多商户) / `GROUP`(集团跨景区) |
| `scope_id` | bigint | 对应 `scope` 的归属 ID |
| `rule_type` | enum | `FULL_REDUCTION`(满减) / `DISCOUNT`(折扣) / `GIFT`(买赠) / `POINT_BONUS`(消费送积分) / `COUPON`(赠券) / `CASHBACK`(返现) |
| `conditions` | json | 适用条件：商品范围/商户范围/会员等级/时段等 |
| `actions` | json | 规则动作：满减金额、折扣率、赠品 SKU、积分倍率、券模板 ID、返现比例 |
| `stack_policy` | enum | `EXCLUSIVE`(与其他规则互斥) / `STACKABLE`(可叠加，`stackable_with` 列出可共存的 `rule_type` 列表) |
| `valid_period` | json | |
| `status` | enum | `DRAFT` / `ACTIVE` / `EXPIRED` |
| `cost_allocation_rule_id` | bigint, nullable | `rule_type ∈ {GIFT, CASHBACK}` 时关联二、`CostAllocationRule` |

### 3.2 对外接口

- `GetApplicableRules(cart, user_id) -> [{rule_id, rule_type, discount_detail}]`：order-service 创建订单时调用，返回命中的规则及优惠明细，**快照**到订单（类比 08 文档价格快照机制，避免后续规则变更影响历史订单）。

### 3.3 叠加策略计算顺序

```
1. 筛选 conditions 命中的规则集合 R
2. 按 stack_policy 分组：
   - EXCLUSIVE 规则之间：取优惠力度最大的一条生效，其余忽略
   - STACKABLE 规则：仅当与已选规则的 stackable_with 互相兼容才共同生效
3. 计算顺序（固定，避免歧义）：
   ① DISCOUNT（乘法：单价 × (1-折扣率)，多个 DISCOUNT 叠加为连续乘法）
   ② FULL_REDUCTION（加法：在 ① 结果基础上减去满减金额）
   ③ 会员价（价格中心 PriceCalendar.MEMBER，08 文档既有机制，视为优先级最低的基础折扣，与 ①② 的关系由 stack_policy 显式声明，默认 MEMBER 价与 DISCOUNT 互斥取较优）
4. GIFT/POINT_BONUS/COUPON/CASHBACK 不影响订单金额计算，作为「订单 PAID 后的履约动作」记录在订单快照中，供四/五/二节消费
```

### 3.4 命中记录快照

订单创建时将 3.2 返回结果快照为 `OrderPromotionSnapshot`（归属 order-service 的订单项扩展字段，本文档不重复定义表结构）：`{rule_id, rule_type, discount_amount, gift_sku_id?, point_bonus?, coupon_template_id?, cashback_amount?}[]`，订单 `PAID` 后按此快照触发：积分发放（1.3 `PointLedger(EARN)`）、赠券发放（四、`CouponInstance`）、返现入账（1.4 `WalletLedger(REFUND)`，语义上是"获得"但归档在 `REFUND` 类型下以区分充值）、买赠/返现的成本分摊（二）。

| 字段（GroupInstance） | 类型 | 说明 |
|---|---|---|

**状态机**：

```
FORMING ──member_count达到group_size──▶ SUCCESS ──各成员订单按group_price转为PAID(走07订单流程)
   │

```

- 每个参团成员在 `GroupInstance.status=FORMING` 期间即创建订单并完成支付（按 `group_price` 预占库存与扣款），但订单状态标记 `PENDING_GROUP_RESULT`（07 文档订单状态机的扩展分支，不在本文档重复定义订单状态机全貌）；`SUCCESS` 后批量确认（07 文档 `ConfirmReservation`），`FAILED` 后批量退款并释放库存。
