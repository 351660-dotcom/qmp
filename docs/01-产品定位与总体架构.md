# 01 · 产品定位与总体架构

## 一、产品定位

一套面向景区文旅行业的多租户 SaaS 系统，服务对象为**文旅集团及其下属景区、商户**。核心价值：

- **多业态统一平台**：门票、酒店、餐饮、零售、游乐、剧院、游船等业态在一套系统内经营、交易、核销、结算。
- **高并发可靠**：支撑重大节假日的访问与交易峰值，保障「下单—支付—核销」黄金链路不崩。
- **离线可用**：景区断网或云端异常时，核销不停摆。
- **资金合规**：通过持牌机构资金存管实现多级分账，不触碰二清红线。
- **硬件一体**：闸机、PDA、自助机、人脸终端等统一接入与运维。
- **AI 原生**：产品内置 AI 能力（运营/报表/营销/客服），且工程体系本身 AI 友好，便于 AI 持续二开。
- **API-First 开放平台**：每个功能皆有 API 与对接规范，支持与第三方双向对接。

## 二、四级租户模型

```
平台运营方（SaaS 提供商）
 └─ 文旅集团（租户：独立数据域、独立结算主体、独立品牌）
     └─ 景区（业务单元：独立闸机、客流、预约规则、承载量）
         └─ 商户（结算主体：分账与对账的最小单位）
             └─ 门店 / 点位 / 设备（核销与收银的物理位置）
```

- 所有业务表带 `tenant_id`，逻辑隔离 + 按租户分库分表。
- 大型集团客户支持独立库、独立部署（混合租户模式）。
- **商户是结算主体**：分账、对账、提现挂在商户上，决定支付进件做到商户级。

## 三、业态抽象：五种库存模型

七种业态本质抽象为「商品 × 资源 × 库存模型」，统一为五类库存：

| 库存模型 | 适用业态 | 库存维度 |
|---|---|---|
| 日期库存 | 门票（分时预约） | 日期 + 时段 + 票种 |
| 场次库存 | 剧院演出、游船班次、游乐项目 | 场次 |
| 座位库存 | 剧院（选座）、游船舱位 | 场次 + 座位图 |
| 房晚库存 | 酒店 | 房型 + 价格日历 + 连住 |
| 实物 SKU | 零售、餐饮 | 数量 |

在其上构建**组合商品（套票）**：跨业态、跨商户一单购买，订单拆单 + 按订单分账。此能力须自第一天设计进去，后补代价极大。

行业政策性需求：实名制购票、分时预约（文旅部对 A 级景区要求）、团队票（旅行社渠道）、年卡/月卡（常配人脸核验）。

## 四、技术栈

- **后端**：Java / Spring Cloud Alibaba（Nacos 注册配置、Sentinel 限流熔断、Seata 分布式事务、RocketMQ、ShardingSphere 分库分表）。
- **存储**：MySQL（交易）、Redis 集群（缓存/库存扣减）、Elasticsearch（搜索）、ClickHouse 或 Apache Doris（数据分析）、对象存储（抽象层，适配阿里 OSS / 腾讯 COS / MinIO）。
- **前端 C 端**：微信小程序 + H5（公众号/短信/一码游）。
- **前端 B 端**：Web 管理后台、商户 PDA App（Android）。
- **部署**：容器化 + K8s（阿里云 ACK / 腾讯云 TKE），不绑定云厂商专有服务，Terraform/Helm IaC，支持私有化交付。

## 五、总体架构分层

```
┌──────────────────────────────────────────────────────┐
│  C 端（小程序/H5）  B 端（管理后台/PDA）  开放平台/第三方  │
├──────────────────────────────────────────────────────┤
│              API 网关（鉴权·限流·防刷·排队）              │
├──────────────────────────────────────────────────────┤
│  业务中台：商品·库存·价格·订单·支付分账·核销·会员营销·渠道  │
│  行业应用：酒店 PMS · 餐饮零售收银                        │
│  支撑域：租户权限·硬件接入·数据中台·AI 能力中心·开放平台    │
├──────────────────────────────────────────────────────┤
│   中间件：Nacos·Sentinel·RocketMQ·Redis·Seata          │
├──────────────────────────────────────────────────────┤
│   数据层：MySQL(分库分表)·ES·ClickHouse/Doris·对象存储   │
└──────────────────────────────────────────────────────┘
        ↕ 与「景区边缘节点」长连接同步（离线核销/设备自治）
```

## 六、高并发与离线设计要点

- **请求分层消化**：静态内容走 CDN + 静态化（挡掉绝大多数读）；动态查询走多级缓存（本地缓存 + Redis 集群）；交易写入才进后端核心链路。
- **交易链路**：网关限流防刷 + 排队机制（超阈值进等待队列而非报错）→ Redis + Lua 原子扣减库存（热点票种库存分桶）→ MQ 削峰异步下单 → 订单按 `tenant_id`+`user_id` 分库分表。
- **弹性**：HPA（Pod）+ Cluster Autoscaler（节点）+ 节假日定时预扩容 + 全链路压测制度。
- **降级预案**：保「下单—支付—核销」黄金链路，非核心功能（推荐/评论/营销页）可降级。
- **离线核销（景区生命线）**：签名票码本地验签（无需联网验真）+ 景区边缘节点维护已核销名单/黑名单，断网续核，恢复后与云端对账。架构为「云端 SaaS + 景区边缘节点」混合形态。

## 七、支付与分账（合规）

- **红线**：平台自行归集资金即二清，禁止。
- **路线**：银行/持牌机构资金存管（通联/汇付/见证宝类）。资金进存管户，按指令分账。
- **分账场景**：按订单项分（套票拆到各商户）、多级抽佣（平台/集团/景区各抽点）、退款分账回退。
- **对账**：渠道账单 vs 平台流水 vs 分账明细，三方日对账，差错处理工作台。
- **通道抽象**：支付中心做通道抽象层，预留多存管通道与服务商分账并存。
