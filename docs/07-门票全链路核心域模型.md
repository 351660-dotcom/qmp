# 07 · 门票全链路核心域模型（库存 + 订单）

> 范围：门票全链路（ADR-005 第一条联调链路）中最核心、最易出错的两个服务——**库存服务（防超卖）**与**订单服务（状态机）**。
> 商品/价格/支付分账/核销/会员服务在本文中仅作为依赖以字段形式出现（如 `sku_id`、`price_snapshot`），各自的完整域模型在后续迭代补充。
> 部署形态：按 2026-06-13 确认，本阶段为「模块化单体」——各服务是独立 Maven 模块 + 独立 schema（数据库可不同 database 但同实例），模块间只能通过本文定义的接口/事件交互，不允许跨模块直接访问对方表，为后续物理拆分预留路径。
> ADR-025（2026-06-14）：本文 1.1~1.4 的 `inventory_bucket`/`InventoryReservation` 表结构与防超卖两道防线/预占状态机，作为「日期/场次型」库存的**参考实现（reference implementation）**，其设计模式抽象为共享代码库 `inventory-kernel`；酒店房晚库存、会议室场次库存等其他业务域**各自独立建表**接入该共享逻辑，不与本服务共表（见 11 文档）。

## 一、库存服务（inventory-service）

### 1.1 聚合根：InventoryBucket（库存桶）

对应 v0.2 第 4 节「五种库存模型」中的**日期库存**（门票场景：日期 + 时段 + 票种 SKU）。

| 字段 | 类型 | 说明 |
|---|---|---|
| `bucket_id` | bigint (PK) | 库存桶 ID |
| `tenant_id` | bigint | 集团租户 ID（分库分表 key 之一） |
| `scenic_id` | bigint | 景区 ID |
| `sku_id` | bigint | 门票 SKU（票种，对应商品中心） |
| `sale_date` | date | 可售日期 |
| `time_slot_id` | bigint, nullable | 分时预约时段（无分时预约则为 0/null） |
| `total_quota` | int | 当日该时段总库位数 |
| `sold_count` | int | 已售出（已确认）数量 |
| `locked_count` | int | 预占中（未确认）数量 |
| `channel_quota` | json | 渠道库存分配，v1 仅 `{"direct": total_quota}` |
| `version` | int | 乐观锁版本号 |

**核心不变式**：`sold_count + locked_count <= total_quota`，任何写操作必须在该约束下进行（DB 条件更新保证）。

### 1.2 实体：InventoryReservation（预占记录）

| 字段 | 类型 | 说明 |
|---|---|---|
| `reservation_id` | varchar (PK) | **由调用方（order-service）生成并传入**，建议取 `order_item_id`，作为幂等键 |
| `bucket_id` | bigint | 关联库存桶 |
| `quantity` | int | 预占数量 |
| `status` | enum | `HOLDING` / `CONFIRMED` / `RELEASED` / `EXPIRED` |
| `hold_expire_at` | datetime | 预占超时时间（创建时 = now + 15 分钟，可配置） |
| `created_at` / `updated_at` | datetime | |

### 1.3 防超卖两层防线（落地 ADR-018 / 06-库存与防超卖设计.md）

```
第一道防线（Redis，快速失败）          第二道防线（DB，最终一致，不超卖兜底）
┌─────────────────────────┐         ┌──────────────────────────────────────┐
│ key: INV:{bucket_id}      │         │ UPDATE inventory_bucket               │
│ value: remain (剩余可售)   │  异步   │   SET locked_count = locked_count + N │
│ Lua: DECRBY 原子扣减       │ ───────▶│   WHERE bucket_id = ?                 │
│   若 remain < N 则失败     │  MQ    │     AND total_quota - sold_count      │
│ 热点桶: 按 bucket_id hash  │         │           - locked_count >= N          │
│   分 N 个 sub-key 分摊      │         │ 影响行数 = 0 → 与 Redis 不一致，告警    │
└─────────────────────────┘         └──────────────────────────────────────┘
```

- **Redis 是性能层**：挡掉绝大多数无效请求（库存已售罄时秒级返回失败），不是最终真相源。
- **DB 是最终真相源**：条件更新影响行数为 0 时，说明 Redis 计数与 DB 不一致（如 Redis 重启丢数据），此时**以 DB 结果为准**，若 DB 也拒绝则该次预占整体失败，并触发对账告警（修正 Redis 计数）。
- **Redis 初始化/恢复**：服务启动或对账发现不一致时，按 `remain = total_quota - sold_count - locked_count`（DB 值）重建 Redis key。

### 1.4 预占生命周期与幂等

| 操作 | 调用方 | 前置状态 | 后置状态 | 库存数字变化 |
|---|---|---|---|---|
| `CreateReservation(reservation_id, bucket_id, qty)` | order-service（创建订单时，同步调用） | 不存在 | `HOLDING` | Redis: `remain -= qty`；DB: `locked_count += qty` |
| `ConfirmReservation(reservation_id)` | order-service（支付成功事件触发） | `HOLDING` | `CONFIRMED` | DB: `locked_count -= qty`, `sold_count += qty`（同事务条件更新） |
| `ReleaseReservation(reservation_id)` | order-service（取消/超时/退票） | `HOLDING` 或 `CONFIRMED` | `RELEASED` | DB: 对应字段 `-= qty`；Redis: `remain += qty` |
| `ExpireReservation`（定时任务，扫描 `hold_expire_at < now AND status=HOLDING`） | 系统内部 | `HOLDING` | `EXPIRED` | 同 Release |

**幂等保证**：
- `reservation_id` 全局唯一且由调用方指定 → `CreateReservation` 若发现记录已存在，直接返回已有结果（不重复扣减），用于应对 order-service 的网络重试。
- 所有状态转换均要求"前置状态匹配"，否则返回当前状态而非报错（如对已 `CONFIRMED` 的记录再次调用 `ConfirmReservation` 返回成功但不重复执行）。

## 二、订单服务（order-service）

### 2.1 聚合根：Order

| 字段 | 类型 | 说明 |
|---|---|---|
| `order_id` | bigint (PK) | 订单 ID（分库分表：`tenant_id` + `user_id`） |
| `tenant_id` / `scenic_id` / `merchant_id` | bigint | 归属 |
| `user_id` | bigint | 下单用户 |
| `status` | enum | 见 2.4 订单状态机（**粗粒度**） |
| `total_amount` | decimal | 应付金额（价格中心快照） |
| `paid_amount` | decimal | 实付金额 |
| `refund_amount` | decimal | 累计退款金额 |
| `pay_expire_at` | datetime | 支付超时时间（创建时 = now + 15 分钟） |
| `payment_id` | varchar, nullable | 关联支付单（payment-service） |
| `version` | int | 乐观锁版本号 |

### 2.2 实体：OrderItem（订单项）

| 字段 | 类型 | 说明 |
|---|---|---|
| `order_item_id` | bigint (PK) | 同时作为库存预占的 `reservation_id` |
| `order_id` | bigint | 所属订单 |
| `sku_id` / `sale_date` / `time_slot_id` | - | 对应库存桶维度 |
| `quantity` | int | 购买数量 |
| `unit_price` / `subtotal` | decimal | 价格中心快照（防止后续改价影响历史订单） |
| `refund_policy_snapshot` | json | 下单时快照的退改规则（阶梯退费比例等） |

### 2.3 实体：TicketCredential（核销凭证）

> 归属核销服务（ticket-verification-service），但与 `order_item_id` 一对多关联（一个 OrderItem 的 `quantity` 张票各对应一条凭证，支撑「一票一证」与单张票的部分退改）。

| 字段 | 类型 | 说明 |
|---|---|---|
| `credential_id` | bigint (PK) | |
| `order_item_id` | bigint | |
| `ticket_index` | int | 第几张票（1..quantity） |
| `verify_code` | varchar | 核销凭证码（二维码内容，签名串，支持离线验签） |
| `status` | enum | `UNUSED` / `VERIFIED` / `REFUNDING` / `REFUNDED` / `VOIDED` / `EXPIRED` |
| `verified_at` / `verify_terminal_id` | - | 核销记录 |

### 2.4 订单状态机（粗粒度，Order.status）

```
                 ┌──────────────────┐
   创建订单+预占库存│  PENDING_PAYMENT  │
   ───────────────▶│ (待支付,15min超时) │
                 └─────────┬─────────┘
                   支付成功 │         │ 超时 / 用户取消
                            ▼         ▼
                 ┌──────────────────┐  ┌───────────┐
                 │       PAID        │  │ CANCELLED │ (终态)
                 │ (库存已确认,凭证已出)│  └───────────┘
                 └─────────┬─────────┘
                            │ 所有 TicketCredential
                            │ 到达终态(VERIFIED/REFUNDED/VOIDED/EXPIRED)
                            ▼
                 ┌──────────────────┐
                 │      CLOSED       │ (终态)
                 └────────────────────┘
```

- `PENDING_PAYMENT → CANCELLED`：触发 `ReleaseReservation`（所有该订单的 OrderItem）。
- `PENDING_PAYMENT → PAID`：触发 `ConfirmReservation` + 生成 `TicketCredential`（每个 OrderItem 按 quantity 生成）+ 通知 payment-service 发起分账。
- `PAID → CLOSED`：由 TicketCredential 状态变化事件驱动判定（所有凭证终态后聚合更新 Order.status）。

### 2.5 票据状态机（细粒度，TicketCredential.status）

```
UNUSED ──核验通过──▶ VERIFIED (终态)
   │
   ├──申请退票(核验前,符合退改规则)──▶ REFUNDING ──退款完成──▶ REFUNDED (终态)
   │                                                  └─退款失败──▶ UNUSED (回退)
   │
   └──超过有效期未核验──▶ EXPIRED (终态)

VERIFIED ──(v1 不支持已核销退票，VOIDED 留作异常作废用，如误核销人工撤销)
```

- `REFUNDING → REFUNDED` 时，若该票对应的库存桶仍在「可释放窗口」内（业务规则，如游玩日期前 N 小时），同步触发 `ReleaseReservation` 释放 1 个库存名额；超出窗口则不释放（库存仍记为已售，但票务终态为已退款，体现"过期不退库存"的业务规则）。
- `VOIDED` 为人工/客服在异常订单处理工作台中使用（v0.2 第 6 节新增），v1 先预留状态值，不实现操作入口。

## 三、下单 → 支付 → 核销 全链路时序

```
C端          order-service        inventory-service   payment-service   ticket-verification
 │  创建订单      │                      │                  │                  │
 ├──────────────▶│  CreateReservation   │                  │                  │
 │                ├─────────────────────▶│ (Redis扣减+DB预占)│                  │
 │                │◀─────────────────────┤ HOLDING          │                  │
 │   订单(PENDING_│                       │                  │                  │
 │◀───PAYMENT)────┤                       │                  │                  │
 │  发起支付       │                       │                  │                  │
 ├────────────────┼──────────────────────┼─────────────────▶│ 创建支付单        │
 │  (微信/支付宝完成支付，异步回调)                            │                  │
 │                │◀──────────────────────────────PaymentSucceeded(event)       │
 │                │  ConfirmReservation  │                  │                  │
 │                ├─────────────────────▶│ CONFIRMED         │                  │
 │                │  通知发起分账          │                  │                  │
 │                ├───────────────────────────────────────▶│ 分账(存管通道)     │
 │                │  生成核销凭证           │                  │                  │
 │                ├──────────────────────┼──────────────────┼─────────────────▶│
 │   订单(PAID)    │                       │                  │   UNUSED凭证×N    │
 │◀───────────────┤                       │                  │                  │
 │                                                            │                  │
 │  到园核验(扫码) │                                           │                  │
 ├─────────────────────────────────────────────────────────────────────────────▶│
 │                                                            │  VERIFIED        │
 │                │◀────────────────TicketVerified(event)─────────────────────────┤
 │                │ 更新凭证聚合状态，                                              │
 │                │ 全部VERIFIED则Order→CLOSED                                     │
```

**关键设计原则**：
1. **预占在创建订单时同步完成**（不能等支付才占库存，否则下单瞬间无法准确告知用户库存是否充足）。
2. **支付成功是异步事件驱动**（微信/支付宝回调有延迟和重复投递风险，`ConfirmReservation`/凭证生成/分账三步都必须幂等，且建议放在同一个本地事务 + MQ 事务消息中保证原子性）。
3. **核销不依赖订单服务在线**（核销凭证一旦生成即下发到边缘节点，核验通过后才异步回报订单服务更新状态，满足离线核销的非功能性需求）。
