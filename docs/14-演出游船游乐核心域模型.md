# 14 · 演出/游船/游乐核心域模型

> 范围：功能清单第 3 节「演出」「游船/游乐」、第 4 节「场次库存/座位库存」两类库存模型，以及第 13 节提及的「温泉/水乐园二次消费账户（手牌/腕带余额）」。
> 部署形态：新增 Maven 模块 **performance-service**，管理「场次资源」与「座位/舱位资源」两类库存，以及手牌/腕带二次消费账户。
> 按 **ADR-025**：`session_inventory_bucket` / `seat_inventory_bucket` 为 performance-service **独立建表**，字段范式与防超卖两道防线/预占状态机复用 07 文档 `inventory_bucket`/`InventoryReservation` 的设计（通过共享代码库 `inventory-kernel`），不与门票域共表、不调用 inventory-service API。
> 订单聚合根仍为 07 文档的 `Order`/`OrderItem`（不像 11 文档酒店那样另起 `Reservation` 聚合）——演出/游船/游乐的一次购买结构上等价于"一个 OrderItem 预占一个场次/座位库存桶"，与门票购买同构，故直接复用 order-service，仅在 `OrderItem` 上扩展 `session_id`/`seat_id` 等维度字段（见一、二节）。

## 一、场次库存（无座位业态：游船班次 / 游乐项目）

对应「五种库存模型」中的**场次库存**——库存维度为「场次」，不含座位图（剧院/舱位见二节）。

### 1.1 实体：PerformanceSession（场次）

| 字段 | 类型 | 说明 |
|---|---|---|
| `session_id` | bigint (PK) | 场次 ID |
| `tenant_id` / `scenic_id` | bigint | |
| `sku_id` | bigint | 关联商品中心 SKU（如"摇橹船 30 分钟体验""丛林飞车"） |
| `session_date` | date | 场次日期 |
| `start_time` / `end_time` | time | 班次起止时间 |
| `status` | enum | `SCHEDULED` / `CANCELLED`（场次因天气/设备故障取消，触发该场次所有 `OrderItem` 退票） |

### 1.2 聚合根：session_inventory_bucket（场次库存桶，独立表）

| 字段 | 类型 | 说明 |
|---|---|---|
| `bucket_id` | bigint (PK) | |
| `tenant_id` / `scenic_id` | bigint | |
| `session_id` | bigint | 关联 1.1，**场次库存桶维度 = `session_id`**（对照 07 文档票务桶维度 `sale_date`+`time_slot_id`） |
| `total_quota` | int | 该场次总容量（游船载客量 / 游乐项目单批次容量） |
| `sold_count` / `locked_count` | int | 同 07 文档 1.1 |
| `channel_quota` | json | 同 07 文档 1.1 |
| `version` | int | 乐观锁 |

- 防超卖两道防线、`session_inventory_reservation` 表（结构同 07 文档 1.2 `InventoryReservation`，仅 `bucket_id` 指向本表）、预占生命周期与幂等规则，**完全复用 `inventory-kernel`**，不再重复描述（见 07 文档 1.3/1.4）。
- `CreateReservation(reservation_id, bucket_id, qty)` 中 `reservation_id` 仍取 `order_item_id`。

### 1.3 安全限制声明：SafetyDeclarationSnapshot

> 对应功能清单「安全限制（身高/年龄/健康声明）」。

| 字段 | 类型 | 说明 |
|---|---|---|
| 归属 | - | `OrderItem` 扩展字段（不单独建表），下单时由前端采集并随订单一起提交 |
| `safety_rule_snapshot` | json | 下单时从 `sku_id` 配置快照该 SKU 的限制规则：`{height_limit_cm, age_limit, health_declaration_required}` |
| `declaration_answers` | json | 用户填报：`{height_cm?, age?, health_declaration_confirmed: bool}` |

- **校验时机**：
  - 下单时：若 `declaration_answers` 不满足 `safety_rule_snapshot` 的硬性条件（如年龄上限），order-service 直接拒绝创建订单（不预占库存）。
  - 登船/入园检票时：核销终端（核销中心）在核验通过界面**展示** `safety_rule_snapshot` 供工作人员目视核查（如身高），v1 不做硬件联动（人脸/身高仪二期视设备接入需求评估）。
- 该快照与 07 文档 `OrderItem.refund_policy_snapshot` 同级，均为下单时固化的只读快照。

## 二、座位库存（剧院选座 / 游船舱位）

对应「五种库存模型」中的**座位库存**——库存维度为「场次 + 座位图」。**关键设计**：座位库存桶按"单座位/单舱位"为粒度，本质是 `total_quota` 通常为该座位容量（剧院座位=1，游船舱位可载多人则为舱位定员）的库存桶——**复用一节同一套 `inventory-kernel`，不是另一种机制**，只是粒度更细（每个座位/舱位一条桶记录）。

### 2.1 实体：SeatMap + Seat（座位图模板）

| 字段（SeatMap） | 类型 | 说明 |
|---|---|---|
| `seat_map_id` | bigint (PK) | 座位图模板 ID（一个剧场/一艘船的布局，可被多个 `session_id` 复用） |
| `tenant_id` / `scenic_id` | bigint | |
| `venue_name` | varchar | 剧场名/船名 |
| `layout_meta` | json | 座位图渲染元数据（行列范围、过道、舞台方向等，前端用） |

| 字段（Seat） | 类型 | 说明 |
|---|---|---|
| `seat_id` | bigint (PK) | |
| `seat_map_id` | bigint | |
| `seat_no` | varchar | 座位编号（如 `A排12号` / `3层 301舱`） |
| `seat_zone` | varchar | 票区/座位等级（如"VIP区""标准舱"），与价格中心按 `(sku_id, seat_zone)` 定价关联（见三节） |
| `capacity` | int | 该座位/舱位可容纳人数。剧院座位 = 1；游船舱位可 > 1（按整舱位售卖时） |
| `position` | json | 渲染坐标 `{x, y}` |

### 2.2 聚合根：seat_inventory_bucket（座位库存桶，独立表）

| 字段 | 类型 | 说明 |
|---|---|---|
| `bucket_id` | bigint (PK) | |
| `tenant_id` / `scenic_id` | bigint | |
| `session_id` | bigint | 关联 1.1（同一场场次下的每个座位各一条桶记录） |
| `seat_id` | bigint | 关联 2.1 |
| `total_quota` | int | = `Seat.capacity`（建场次时按 `SeatMap` 批量初始化生成） |
| `sold_count` / `locked_count` | int | 同上；`(session_id, seat_id)` 唯一 |
| `version` | int | 乐观锁 |

- 预占/确认/释放、防超卖两道防线**复用 `inventory-kernel`**，与 1.2 同一套代码、不同表。
- **舱位整体售卖** vs **单座出售**：若 `Seat.capacity > 1` 且按整舱位售卖（`OrderItem.quantity = capacity`，一次性占满该桶），与按人数零售（`quantity < capacity`，多个 `OrderItem` 共占同一桶直至 `sold_count+locked_count = total_quota`）是同一套桶机制下的两种业务用法，由商品中心 SKU 定义决定，不影响库存模型本身。

### 2.3 选座下单流程与并发

```
1. C 端请求 GetSeatMapStatus(session_id)
   → performance-service 批量查询该 session 下所有 seat_inventory_bucket
   → 返回 [{seat_id, status: AVAILABLE/LOCKED/SOLD}]（status 由 total_quota-sold_count-locked_count 推导）

2. 用户选定座位 → order-service 创建订单
   → 对每个选中座位调用 CreateReservation(reservation_id=order_item_id, bucket_id=<该座位桶>, qty)
   → 第一道防线 Redis Lua 对 remain=1（或 capacity）的 key 做 DECRBY：
       两个用户同时选中同一座位时，仅一个成功，另一个立即收到"座位已被选定"提示
   → 成功的座位进入 HOLDING（hold_expire_at，建议选座场景缩短为 5~10 分钟，可配置，
     比 07 文档票务默认 15 分钟更短，因用户处于"挑选中"的强实时交互场景）

3. 座位图实时刷新：座位 HOLDING/RELEASED/CONFIRMED 状态变化通过 WS/SSE 推送给同一
   session 的所有在线用户，避免轮询；推送内容仅为 {seat_id, status}，不含用户信息
```

- `OrderItem` 扩展字段：`session_id`、`seat_id`（座位库存场景）或仅 `session_id`（一节无座位场景），与 07 文档既有 `sku_id`/`sale_date`/`time_slot_id` 并列，由 `bucket_ref` 指明本订单项对应的库存桶归属（`TICKET` / `SESSION` / `SEAT`），决定 order-service 调用 inventory-service 还是 performance-service 的 `CreateReservation`——**接口形态一致**（ADR-025），order-service 只需按 `bucket_ref` 路由。

### 2.4 退改与座位释放

- 与 07 文档票据状态机一致：`TicketCredential.status: REFUNDING → REFUNDED` 时触发 `ReleaseReservation`，释放该座位桶的 `sold_count`，座位重新变为 `AVAILABLE`（若距场次开始时间仍在可退窗口内）。
- **场次取消**（`PerformanceSession.status=CANCELLED`，如台风停航）：批量触发该 `session_id` 下所有 `OrderItem` 的全额退款 + `ReleaseReservation`，由 performance-service 发起 `SessionCancelled` 事件，order-service 订阅处理（批量退款走 08 文档 payment-service 退款接口，不在本文档重复定义）。

## 三、票区定价（与商品/价格中心的关系）

- 「票区/座位等级定价」属于商品中心与价格中心范畴：`PriceCalendar`（08 文档）按 `(sku_id, seat_zone)` 维度定义价格，而非按单个 `seat_id`——即同一票区内所有座位价格一致。
- performance-service 不持有价格数据，仅在 `GetSeatMapStatus` 返回结果中附带 `seat_zone`，由前端结合价格中心返回的 `(sku_id, seat_zone) → price` 映射渲染"选座价格地图"。

## 四、温泉/水乐园二次消费账户（手牌/腕带）

> 对应功能清单第 13 节「温泉/水乐园二次消费账户（手牌/腕带余额）」，归入游乐业态。与 13 文档 `MemberWallet`（注册会员储值，集团级）是**两种不同载体**：手牌账户绑定**物理介质（NFC 腕带/卡）**，**可匿名开通**（游客现场办理，无需注册会员），退场时一次性结算；`MemberWallet` 绑定**用户账号**，长期有效、跨次入园延续。两者通过 `user_id` 关联可选打通（见 4.3）。

### 4.1 聚合根：WristbandAccount

| 字段 | 类型 | 说明 |
|---|---|---|
| `wristband_id` | varchar (PK) | 物理腕带/卡的 NFC UID |
| `tenant_id` / `scenic_id` | bigint | |
| `user_id` | bigint, nullable | 可选绑定会员账号（见 4.3），现场匿名办理时为空 |
| `balance` | decimal | 二次消费余额 |
| `deposit_amount` | decimal | 押金（办理时收取，退还时结算） |
| `status` | enum | `ACTIVE`(在场使用中) / `SETTLED`(已退场结算) / `LOST`(挂失，余额冻结) |
| `issued_at` / `settled_at` | datetime | |

### 4.2 账本：WristbandLedger

| 字段 | 类型 | 说明 |
|---|---|---|
| `ledger_id` | bigint (PK) | |
| `wristband_id` | varchar | |
| `change_amount` | decimal | 正数=充值/退款，负数=消费 |
| `balance_after` | decimal | |
| `type` | enum | `TOPUP`(充值) / `CONSUME`(消费) / `REFUND`(退场退余额) / `DEPOSIT`(收押金) / `DEPOSIT_REFUND`(退押金) |
| `merchant_id` | bigint, nullable | `CONSUME` 时记录消费商户（园内储值消费同样涉及分账，与 13 文档 `WalletLedger.merchant_id` 同一思路：消费时从"押金/储值专户"实时分账给商户） |
| `source_ref` | varchar | `(source_ref, type)` 唯一，幂等键，与 13 文档账本设计模式一致 |

- 接口：`DeductWristbandBalance(wristband_id, amount) -> {success, remaining_balance}`，与 13 文档 `DeductWallet`/12 文档 `DeductWallet` 同构，供 dining-pos-service（12 文档）结账时新增「手牌支付」方式调用。
- **退场结算**（`ACTIVE → SETTLED`）：`balance` 退还（原支付渠道或现金柜台）+ `deposit_amount` 退还（核验腕带完好），生成 `REFUND`/`DEPOSIT_REFUND` 两条账本记录；`LOST` 状态下 `balance` 冻结待人工核实，不可消费/退款。

### 4.3 与会员体系的可选打通

- 办理手牌时若用户出示会员码（扫码绑定 `user_id`），后续 `CONSUME` 记录可选择性同步触发 13 文档 `PointLedger(EARN)`（按消费金额折算积分），打通逻辑由 marketing-service 订阅 `WristbandLedger(CONSUME)` 事件实现，不要求 performance-service 感知会员规则（保持模块解耦，对应 ADR-005 模块化单体原则）。
- 未绑定 `user_id` 的匿名腕带不产生积分，仅完成现场二次消费与退场结算。
