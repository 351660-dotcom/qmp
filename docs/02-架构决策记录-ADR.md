# 02 · 架构决策记录（ADR）

> 每条记录一个已确认的关键决策，含背景与理由。后续新决策追加编号，不删除历史（变更则新增一条说明取代关系）。

## ADR-001 后端技术栈：Java / Spring Cloud Alibaba
- **决策**：采用 Java + Spring Cloud Alibaba 微服务体系。
- **理由**：国内文旅/电商领域生态最成熟，Nacos/Sentinel/Seata/RocketMQ 配套齐全，招聘最容易，OTA 与支付存管通道 SDK 支持最好。
- **状态**：已确认（2026-06-12）。

## ADR-002 部署形态：公有云 SaaS + 支持私有化部署
- **决策**：以公有云 SaaS 为主，架构从第一天即支持私有化交付。
- **理由**：部分大集团/国企客户要求部署在自有机房。私有化能力（去云厂商绑定、license、版本分发）后补代价大。
- **影响**：中间件全部用开源系；对象存储、消息、缓存等做抽象层。
- **状态**：已确认（2026-06-12）。

## ADR-003 多云支持：阿里云 + 腾讯云，不绑定专有服务
- **决策**：同时支持阿里云（ACK）与腾讯云（TKE），K8s 统一应用层，仅基础设施层适配。
- **理由**：客户云环境不一；与 ADR-002 私有化同属「去厂商绑定」纪律。
- **影响**：自动伸缩三层（HPA + Cluster Autoscaler + 节假日定时预扩容）；Terraform/Helm 基础设施即代码，一套描述参数化输出多环境。
- **状态**：已确认（2026-06-12）。

## ADR-004 分账路线：银行/持牌机构资金存管
- **决策**：走持牌机构资金存管（通联/汇付/见证宝类），不走平台自归集（二清）。
- **理由**：多级分账（集团抽成 + 景区抽成 + 商户结算）灵活、合规、可大额结算。
- **影响**：支付中心做通道抽象层，预留服务商分账并存；商户入驻含存管进件 KYC。
- **状态**：已确认（2026-06-12）。

## ADR-005 建设节奏：全功能并行开发
- **决策**：按全功能并行推进，非 MVP 单点切入。
- **理由**：用户业务诉求要求一次成型的完整平台。
- **缓解**：先用一段时间定领域模型与服务契约，门票全链路作为第一条联调打通的链路，降低并行风险。
- **状态**：已确认（2026-06-12）。

## ADR-006 C 端渠道：微信小程序 + 支付宝小程序 + H5
- **决策**：C 端覆盖微信小程序、支付宝小程序、H5（公众号/短信链接/一码游）。不做独立 App，不做抖音小程序。
- **理由（不做抖音）**：抖音开发者服务商申请繁琐，小程序审核常不通过。
- **更新记录**：2026-06-12 初版仅微信 + H5；同日补充支付宝小程序、排除抖音（见 Q6）。
- **状态**：已确认（2026-06-12）。

## ADR-007 酒店：自建完整 PMS
- **决策**：酒店业态自建完整 PMS（房态、排房、前台接待、夜审、门锁、公安旅业对接），不仅做售卖。

- **风险**：工程量极大（对标绿云/石基十余年积累），排期与团队按此量级认知。
- **状态**：已确认（2026-06-12）。

## ADR-010 AI 原生：工程 AI 友好 + 产品内置 AI
- **决策**：系统出身即符合 AI 规范。
  - **工程侧**：每服务带 CLAUDE.md/AGENTS.md、ADR、OpenAPI 契约先行、MQ 事件 Schema 注册、统一脚手架、黄金链路高覆盖测试 + CI 机器反馈、docker compose 一键本地环境、显式优于隐式。
  - **产品侧**：AI 网关（多模型/租户配额/脱敏）、租户级 RAG 知识库、全部业务 API 暴露 MCP/tool-use Agent 接口层。
- **理由**：未来二开扩展由 AI 完成，上下文可达性与可验证性是 AI 开发效率的关键。
- **状态**：已确认（2026-06-12）。

## ADR-011 API-First + 开放平台
- **决策**：每个功能都必须有对应 API 与第三方对接规范，支持双向对接。
  - API 是第一公民，UI/小程序/PDA/第三方平等消费同一套 API。
  - 对外开放平台：开发者门户、应用注册、API Key/OAuth2、租户+应用级 scope、限流配额计量计费、调用审计、Webhook 回调（签名+重试）、沙箱、API 版本化。
  - 对接第三方：适配层 + 防腐层隔离外部协议，每类对接有接入规范文档。
  - 统一规范：鉴权/错误码/分页/幂等/签名/回调格式全平台一致。
- **状态**：已确认（2026-06-12）。

## ADR-013 C 端小程序：每租户独立小程序 + 第三方平台代开发（微信 + 支付宝双平台）
- **决策**：每个租户（集团/景区）拥有各自独立的微信小程序与支付宝小程序，采用第三方平台代开发模式，双平台对称建设。
- **理由**：品牌独立；各租户用自身主体收款，与资金存管分账衔接最顺（资金进各自存管户，分账清晰）。
- **影响 / 需建设**：
  - 申请成为微信第三方平台服务商**与支付宝第三方/代运营服务商**（两套开放平台接口）。
  - 模板小程序 + 一键复制发布：代码模板化，新租户开通时自动创建/配置/提审/发布，**分别向微信和支付宝两个平台发布**。
  - 授权体系：租户授权平台代管理小程序（微信 component/authorizer、支付宝第三方应用授权各一套）。
  - 多租户配置隔离：同一套租户配置按平台加载品牌、页面装修、商品、**支付商户号**。
  - 前端尽量做跨小程序框架（如 Taro/uni-app）以一套代码产出双端，降低双平台维护成本。
- **子决策（暂定 A，待用户最终确认）**：小程序主体归属 —— A）租户用自有小程序账号与商户号（主体清晰，主流做法）；B）平台代为注册管理。当前按 A 设计。
- **状态**：已确认主体模式与双平台范围（2026-06-12）；主体归属暂按 A。

## ADR-014 并发指标基线
- **读链路（PV/QPS）**：目标支撑**百万级/秒**的页面浏览、查余票等读访问。手段：CDN + 页面/商品静态化 + 多级缓存（本地缓存 + Redis 集群），绝大多数读不打到交易后端。
- **写链路（下单 TPS）**：目标 **10,000 单/秒**；超出部分走**排队机制**（候补/等待队列，秒级返回"排队中"，不报错）。
- **设计含义**：
  - 10,000 TPS 用 Redis+Lua 原子扣减 + MQ 削峰异步落库即可稳定达到，无需极端架构。
  - 真正瓶颈是**热点**（爆款景区单一票种被抢，单 key 竞争）→ 重点做**热点库存分桶**。
  - **排队机制为一等公民**，在网关/下单入口设计：超过承接力进等待队列而非失败。
- **状态**：已确认（2026-06-12）。

## ADR-018 库存防超卖（核心）
- **决策**：库存防超卖采用「分层漏斗 + 两道防线」。Redis 预扣挡量+快速失败为第一道，DB 带条件更新（`WHERE remain>=N`）为不超卖最终保证，两者不一致以 DB 为准。
- **数量库存**：库存分桶破解单点热点；MQ 按商品分区单线程顺序落库（无锁争抢、不超卖、有序）。
- **座位库存**：座位状态机（可售→锁定 TTL→已售），带条件锁座原子操作 + DB 唯一约束根治一座多卖。
- **多渠道**：共享池 + 渠道封顶；OTA 下单须回调锁库存接口真正占位（幂等）。
- **统一预占模型**：预占→确认→释放，预占带 TTL，超时自动释放。
- **隐形杀手全覆盖**：预占 TTL、预扣落库补偿、幂等 token、实名限购原子计数、对账兜底、Redis 高可用。
- **详见**：[06-库存与防超卖设计.md](06-库存与防超卖设计.md)。
- **状态**：已确认（2026-06-12）。

## ADR-012 AI 产品能力为核心卖点
- **决策**：运营策略、报表分析、营销活动、智能客服的 AI 助力纳入**本期核心**。
  - 运营策略 AI：经营诊断简报、策略建议、异常预警归因。
  - 报表分析 AI：ChatBI 自然语言查数、归因分析。
  - 营销 AI：活动策划助手、自然语言圈人群、文案海报生成、自动复盘闭环。
  - 智能客服：对接订单系统，能真正办理退改等事务。
- **依赖**：数据中台须先建规范的**指标语义层**（metrics layer），优先级提至与交易链路同批设计。AI 助手上限取决于该底座质量。
- **状态**：已确认（2026-06-12）。

## ADR-019 餐饮供应链深度：总部-门店协同（标杆 gap，2026-06-13）
- **决策**：餐饮零售供应链数字化范围从 ADR-008 的「简版进销存」扩展为**总部-门店协同**：总部统一采购计划、多仓库库存管理、门店在线订货并同步至供应链中心接单、库存预警、损耗与成本核算、中央厨房加工配送对接。
- **理由**：哗啦啦、客如云对标显示完整餐饮 SaaS 的连锁客户均要求总部-门店供应链协同，仅做单店进销存无法满足集团型景区餐饮的选型预期；用户确认本期按此范围建设。
- **影响**：餐饮零售收银（功能清单第 10 节）工程量显著增加，领域模型设计阶段需把「供应链中心」纳入与「商品中心/库存中心」同批设计的服务契约范围；数据中台需配套成本/损耗分析报表（第 14 节）。
- **状态**：已确认（2026-06-13）。

## ADR-020 酒店：基础会议室预订（标杆 gap，2026-06-13）
- **决策**：酒店 PMS（ADR-007）增加基础会议室/宴会厅资源建模与场地预订下单能力，不包含完整 MICE（会议销售线索、报价审批、活动执行单等）流程。

## ADR-021 多租户「三不干涉」原则与租户数据自主权（标杆 gap，2026-06-13）
- **决策**：
  1. **三不干涉**：平台不干涉商户的定价策略、不经手/不归集商户资金流（呼应 ADR-004 存管路线）、不挪用商户客户数据用于平台自身或其他租户的营销/分析。
  2. **数据自主权**：每个租户提供标准化数据导出与迁移工具（订单、会员、商品、财务流水），作为开放平台（ADR-011）的产品化能力，而非临时支持工单。
- **理由**：智游宝公开定位强调「三不干涉」是平台型产品建立租户信任的关键；本次 9 份标杆资料的「重点确认项」中几乎都包含「数据是否被锁定、能否导出迁移」，是客户选型的高频顾虑点，提前产品化可作为差异化卖点。
- **影响**：租户权限与数据隔离设计（功能清单第 2 节）需在架构文档中显式声明该原则；开放平台（第 16 节）的服务契约中需包含数据导出 API。
- **状态**：已确认（2026-06-13）。

## ADR-022 硬件设备身份：SN 码白名单授权机制（用户复核新增，2026-06-14）
- **决策**：每台接入平台的物理硬件设备（闸机/PDA/自助机/腕带读写器等）以 SN 码为身份标识，需在平台注册并获得设备级凭证（密钥/证书）后才能调用接口；网关层校验 SN 码处于「已授权」状态，未注册/已吊销的 SN 码直接拒绝（401/403）。
- **理由**：防止设备被克隆或第三方仿造终端接入核销、票务等核心接口，是离线核销（ADR-018）信任链的起点——离线场景下边缘节点持有的验签密钥本身需要绑定到已授权设备。
- **与 ADR-011 的关系**：ADR-011 的 API Key/OAuth2 面向「第三方应用」级鉴权；本 ADR 的设备凭证面向「物理终端」级鉴权，两者维度不同但统一纳入调用审计。设备状态机：待激活 → 已授权 → 已吊销/已禁用，支持远程吊销（设备丢失/退役）。
- **影响**：硬件接入平台（功能清单第 13 节）新增设备类型字典与 SN 白名单管理；后续硬件域的服务契约设计需包含设备注册/吊销 API 与网关侧校验逻辑。
- **状态**：已确认（2026-06-14）。

## ADR-023 停车场业态：轻量对接而非自建（标杆 gap，2026-06-14）
- **决策**：停车场业态采用轻量集成范围——商品中心新增「停车权益」SKU（按时长/次数），可与门票组合为「门票+停车」套票（功能清单第 3 节）；通过防腐层对接第三方停车系统的计费/通行结果，用于权益核销核对与分账（第 12 节）。不自建车牌识别硬件、道闸控制、独立计费引擎。
- **理由**：趣买票将停车列为与酒店/餐饮并列的全栈子系统，但本平台已有酒店 PMS（ADR-007）与餐饮收银（ADR-008/ADR-019）两大重型自建模块；停车收入对大多数景区/文旅项目是辅助性收入，再新增同等量级的停车子系统会显著增加工程量和团队认知负担，投入产出比不高。用户确认本期按轻量范围建设。
- **影响**：商品中心（第 3 节）新增停车权益 SKU 与「门票+停车」组合产品示例；渠道中心（第 12 节）新增第三方停车系统对接说明，纳入与 OTA/政府码适配层同类的防腐层范围。
- **状态**：已确认（2026-06-14）。

## ADR-024 同行竞品情报数据来源：平台多租户聚合匿名数据（标杆 gap 收尾，2026-06-14）
- **决策**：功能清单第 14 节「同行竞品情报分析」（对标别样红「数据宝」同行调价/收益榜单）二期数据来源采用**平台自身多租户聚合匿名经营数据**，按区域 + 业态 + 规模分组输出榜单、价格区间对比、趋势情报；不自行爬虫采集第三方 OTA/景区官网数据，也不采购第三方文旅大数据服务。
- **理由**：
  - 自行爬虫：反不正当竞争法第 12 条、数据安全法、个人信息保护法均有约束，且存在多起爬虫纠纷判例，目标网站反爬严格、维护成本高，法律与工程风险均不可接受。
  - 采购第三方数据：合规但成本高，本期范围已经很大，新增外部数据采购合同与对接流程会拖慢主线，留待二期视平台规模再评估。
  - 平台自身聚合数据：参考别样红「数据宝」背靠美团酒店生态数据的模式——本平台多租户规模化后即具备类似的数据基础，零外部成本、最合规。
- **影响**：
  - 与 ADR-021「三不干涉」原则协调：聚合匿名基准对比不违反「不挪用商户数据用于其他租户营销/分析」原则的关键在于匿名化 + 足够的聚合粒度（同分组租户数 ≥ N 才输出对标结果），不还原到单一商户。
  - 需在租户服务协议/隐私政策中加入「匿名聚合数据用于行业基准对比」的授权条款。
  - 存在冷启动问题：平台早期租户规模不足时该功能不具备可行性，需设定分组最小样本量门槛，未达标分组不展示对标数据。
  - 功能清单第 14 节「同行竞品情报分析」状态由「❓需先评估数据来源合规性」更新为「数据来源方案已确认，仍列二期，待分组样本量达门槛后启动」。
- **状态**：已确认（2026-06-14）。

## ADR-025 「日期/场次型」库存桶：各业务域独立建表，复用防超卖设计模式而非共享表（2026-06-14）
- **决策**：01 文档「五种库存模型」中「日期库存/场次库存/房晚库存」等"日期+时段"型库存，**不共用同一张 `inventory_bucket` 表**。每个业务域（门票 inventory-service、酒店房晚、会议室场次等）在各自服务内维护**结构相似但独立的库存桶表**（字段范式与 07 文档 `inventory_bucket` 一致：`sku_id`/`sale_date`/`time_slot_id`/`total_quota`/`sold_count`/`locked_count`/`channel_quota`/`version`），各自独立分库分表、独立演进字段。
- **复用的是设计模式与代码，不是表**：ADR-018 的两道防线（Redis Lua 原子扣减 + DB 条件更新 `WHERE total_quota-sold_count-locked_count>=N`）、`InventoryReservation` 预占状态机（`HOLDING`/`CONFIRMED`/`RELEASED`/`EXPIRED`）与幂等保证（07 文档 1.4），抽象为共享代码库（如 `inventory-kernel` 模块），各业务域的库存桶表各自接入该共享逻辑，而非调用同一张表/同一个 inventory-service 的 API。
- **理由**：用户评估后选择此方案——各业态独立加字段、独立容量规划/分片策略互不影响；某业态库存出现性能或数据问题不影响其他业态；跨业态组合产品的库存预占接口形态一致（同一套 SDK/调用约定），调用方感知不到底层是否同表，集成复杂度增量很小。
- **影响**：
  - 07 文档 `inventory_bucket`/`InventoryReservation`/防超卖两道防线，定位调整为「门票域库存桶」+「该设计模式的参考实现（reference implementation）」，其余业务域参考其表结构与状态机自行建表。
  - 11 文档「房晚库存」「会议室场次库存」改为 hotel-pms-service 内部的独立表（`room_inventory_bucket` / `meeting_room_inventory_bucket`），不再描述为"复用 `inventory_bucket`"。
  - 后续新增"日期/场次型"业态（演出场次、游船班次等）均遵循本 ADR：独立建表 + 接入 `inventory-kernel` 共享逻辑。
- **状态**：已确认（2026-06-14）。
